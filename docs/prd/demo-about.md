## 0. Scope & Sequencing Note (read first)

`demo.jerkai.app` ships and renders the real dashboard over synthetic data (`docs/prd/public-demo.md`). It succeeds at showing the product and says nothing about it. The demo's intended traffic is now a link from Albert's LinkedIn profile, which means the modal visitor is a **recruiter, hiring manager, or friend with no context and no obligation to stay** — someone who lands on a stall badge and five stacked charts and has to reverse-engineer, unaided, what they're looking at and why it matters. The dashboard is the artifact; the About surface is the caption that makes the artifact legible in the ten seconds before that visitor leaves.

It also closes an interpretation risk the demo currently carries. The banner says "Demo — synthetic data, not real biometrics," which is a disclaimer, not an explanation. A visitor who notices that the demo has no meal logging and no target setting has no way to tell a *deliberate exclusion* (DL-2026-07-22-b — the write surfaces are omitted so the demo is structurally incapable of writing) from an *unfinished product*. Unstated, absence reads as incompleteness — the exact opposite of the engineering judgment the omission actually represents. The About copy states it plainly, converting the demo's biggest apparent gap into its clearest safety argument.

**Decision — dedicated route `/demo/about`, not an in-page panel (DL-2026-07-25-a).** Considered: (A) a `/demo/about` route in the demo subtree, linked from the demo nav; (B) an expandable About panel or modal on `/demo/weekly`. B was rejected: it is not independently linkable (Albert cannot point a LinkedIn post or a message at the explanation itself), it is not independently indexable, and it adds client-side interactive state to a surface whose entire safety story is "static, DB-free, nothing session-derived." A is a pure static server component in a subtree that already has the isolation guarantee and the proxy exclusion, so it inherits both for free and costs one file plus one nav link. Build A.

**Decision — copy is the full sectioned version, verbatim (DL-2026-07-25-b, revised 2026-07-25).** The page renders the entire body of [[JerkAI - Demo About Page Copy]] from its "About this demo" heading down (the document's title line and the audience/isolation note above the horizontal rule are editorial context for Albert, not page copy) — the sectioned long-form version with its four headed sections ("The problem it solves," "What you're seeing is not real data," "What's intentionally missing," "Why I built it"), not a condensed paragraph. A one-paragraph variant was drafted and considered first, on the theory that a cold visitor decides in seconds and a long page would compete with the dashboard; it was rejected and has since been deleted from the copy document. Rationale for the reversal: the visitor arriving from LinkedIn is evaluating *the person*, not shopping for a product, and the sectioned version is the only form that carries the "Why I built it" argument — metric tree, PRDs with acceptance criteria, AC-named tests — which is the actual reason the demo exists. Skimmable headed sections also let a hurried reader take the first line of each and leave, so length costs less than the compression did. The build agent copies the approved text and does not rewrite, condense, expand, or "improve" it — copy changes are a product-owner decision, not a build-agent one (§8 OQ-2).

**Isolation principle is inherited, not re-argued.** `/demo/about` lives inside the `/demo` subtree, so `proxy.ts`'s existing `demo(?:$|/)` exclusion already makes it public and the existing `tests/unit/demo-isolation.test.ts` guard already walks it — provided the guard is rooted at the new entry too (NFR-56). The page is static text with outbound links: it calls no `auth()`, imports no fixture, imports no DB module, and holds no state.

What this slice is NOT: a rewrite of the demo's dashboards; any change to `proxy.ts`'s matcher or host rewrite (the existing `demo(?:$|/)` exclusion already covers `/demo/about` — verify, do not edit); any change to the synthetic fixture; a GitHub README rewrite (separate work, technical audience); or any new write path.

## 2. Problem statement

A visitor arriving at `demo.jerkai.app` from LinkedIn sees a working dashboard and no explanation of it. They cannot tell what problem it solves, that the numbers are invented (beyond a one-line banner), why the obvious write features are missing, who built it, or where the code lives. The non-technical half of the audience — recruiters, hiring managers, friends — has no path from "charts" to "this person framed a metric tree, wrote the specs, and shipped it solo," which is the entire reason the demo exists. There is also no linkable, indexable page that states what JerkAI is in plain language.

## 3. Objective

A stranger who lands anywhere on the demo can reach an About page in one click that tells them, in four skimmable sections: what JerkAI does, that the data is synthetic and structurally cannot be real, that the write-side features are deliberately excluded (and why that is a safety property, not a gap), and where to find the source and Albert. Success = a non-technical visitor can accurately describe what they just looked at, and a technical visitor has a one-click path to the repo — with the demo's isolation guarantee unchanged and machine-checked.

## 4. Functional Requirements — user-centered acceptance criteria

Written as testable Given/When/Then. "The viewer" = any unauthenticated public visitor. New id prefix **AC-AB** (about), numbered from 1 to avoid collision with the AC-D (dashboard), AC-M (meal), and AC-PD (public demo) series.

* AC-AB1 — Given an unauthenticated visitor, When they navigate to `demo.jerkai.app/about` (resolving to `/demo/about`), Then the About page renders with **no redirect to `/signin`**, inheriting the existing `demo(?:$|/)` gate exclusion with no change to `proxy.ts`.
* AC-AB2 — Given the viewer is on `/demo/weekly` or `/demo/daily`, When they look at the header nav, Then an **About** link is present in the `demo` nav variant and navigates to `/demo/about`; the `live` (authenticated) nav variant is unchanged and shows no About link.
* AC-AB3 — Given the viewer is on the About page, Then it renders the approved copy supplied with this PRD (DL-2026-07-25-b) in full, preserving its section structure: the opening line, **The problem it solves** (noise→trend→driver framing plus the Weekly/Daily two-screen list and the raw-alongside-trend rule), **What you're seeing is not real data**, **What's intentionally missing** (the write features are excluded *by design*, which is what makes the demo safe to publish), **Why I built it**, and the closing GitHub and LinkedIn links. Headings render as real heading elements and the two-screen list as a real list — the copy's structure is what makes it skimmable, so it must not be flattened into prose.
* AC-AB4 — Given the viewer is on the About page, Then the demo banner ("Demo — synthetic data, not real biometrics") still renders above it, inherited from `app/demo/layout.tsx` — the page adds no second, competing disclaimer.
* AC-AB5 — Given the viewer is on the About page, When they use the header nav, Then Weekly and Daily links return them to `/demo/weekly` and `/demo/daily`; the About page is a stop on the demo, not a dead end. Neither resolution link renders as active while on About (the existing `active`-undefined behavior, `app/ui/nav-header.tsx`).
* AC-AB6 — Given the About page's module tree, Then it imports no `lib/db.ts`, no Neon pool, and calls no `auth()` — verified by the existing isolation guard extended to root at this entry (NFR-56). It is strictly read-only static content with outbound links; no form, no state, no mutation CTA (extends AC-PD4/AC-PD5).
* AC-AB7 — Given a search engine or link-preview crawler, Then `/demo/about` carries its own page-level `metadata` (title and description naming it a demo on synthetic data, consistent with NFR-54's locked allow-index posture) rather than silently inheriting the layout's dashboard-oriented title.
* AC-AB8 — Given the authenticated app, When Albert signs in and uses `/weekly`, `/daily`, `/log-meal`, Settings, ingest, and Whoop as before, Then behavior is unchanged by this slice (extends AC-PD6) — the only shared file touched is `app/ui/nav-header.tsx`, and only inside its `demo` branch.
* AC-AB9 — Given a viewer on a phone, Then the About page is readable without horizontal scrolling and its outbound links are tappable — the baseline responsive requirement, called out because this is the surface most likely to be opened from the LinkedIn mobile app.

## 5. Non-Functional Requirements (FDE)

Aligned to [[JerkAI - Architecture & Data Model]]. All prior NFRs remain in force; the following are additive, continuing the series after NFR-55 (Public Demo Surface).

* NFR-56 — **Isolation guard covers the new entry.** `tests/unit/demo-isolation.test.ts` must root its import-graph walk at `app/demo/about/page.tsx` in addition to the existing demo entries, and must fail if that page ever imports `lib/db.ts` or the Neon pool. Adding a demo route without adding it to the guard's entry list is the silent failure mode this NFR exists to prevent — if the guard's entry list is hardcoded, prefer making it enumerate the `app/demo/**` page files automatically so future demo routes are covered by construction.
* NFR-57 — **No matcher edit.** `proxy.ts` must not change. `/demo/about` is already public via `demo(?:$|/)`, and the host rewrite already maps `demo.jerkai.app/about` → `/demo/about` (`url.pathname = /demo${url.pathname}`). Verify both by test rather than by reading — extend `tests/unit/proxy-matcher.test.ts` with an `/demo/about` case and a `demo.jerkai.app/about` rewrite case. If either fails, stop and raise it: an unexpected result here means the demo's gate story is not what the file's comments claim.
* NFR-58 — **Static server component, no client boundary.** The About page is a plain server component rendering static JSX — no `"use client"`, no state, no effects, no data import (not even the synthetic fixture). Outbound links use the appropriate element for their destination (`next/link` for internal nav, plain `<a>` with `rel="noopener noreferrer"` for external).
* NFR-59 — **Copy lives in the component, provenance in the doc.** Render the approved text directly in the page component as static JSX (no CMS, no JSON copy deck, and no markdown-rendering dependency — the copy is a fixed handful of sections, so hand-authored JSX is simpler than any pipeline that parses it), and header-comment the file noting that the wording is product-owner-approved copy (DL-2026-07-25-b) held outside the repo, so the next editor knows changing it is a product-owner decision, not a code change. Do not cite a repo path for the copy; there isn't one — the component is the only in-repo home for this text.
* NFR-60 — **Outbound links are exact and asserted.** Both URLs are resolved (OQ-3, closed): the repo is `https://github.com/albimartai/jerkai` and LinkedIn is `https://linkedin.com/in/albimart`. Ship those exact values — not the profile root `github.com/albimartai`, which lands a visitor on a user page rather than the artifact. A test must assert both hrefs are present and that no `href="#"` or `href=""` survives on the rendered page. Shipping a public portfolio page with a dead link is worse than shipping no page.
* NFR-61 — **Nav change is scoped to the demo variant.** The About link is added inside `nav-header.tsx`'s `variant === "demo"` path only. Existing `live`-variant rendering must be unchanged, asserted by an existing-or-added test that the authenticated header renders no About link. Follow the file's existing comment style when documenting the addition.
* NFR-62 — **Test continuity.** Reuse the existing Vitest projects (`unit`, `component`, `integration`) wired in `vitest.config.ts` — do not create new ones. Render assertions for the About page and the nav link belong alongside the existing `tests/unit/demo-*.test.tsx` files (the established home for `renderToStaticMarkup` demo assertions); the isolation guard extension stays in `tests/unit/demo-isolation.test.ts`; the matcher/rewrite cases in `tests/unit/proxy-matcher.test.ts`. AC ids in every test name.
