## 0. Scope & Sequencing Note (read first)

Withings has no presence anywhere in this repo — confirmed this session via `grep -ri withings` (zero hits) and direct reads of `package.json` (no dependency), `.env.example` (no var), `lib/sources.ts` (`READING_SOURCES = ["fitdays", "whoop", "apple_health"]`, `ACTIVE_SYNC_SOURCES = ["fitdays", "whoop"]`), and both `biometric_readings` and `sync_runs`' `source` check constraints (`('whoop', 'fitdays', 'apple_health')` on both, per `migrations/1783612708597_widen-source-check-apple-health.js` and `migrations/1784053997735_widen-sync-runs-source-apple-health.js`). This is genuinely net-new, not a retrofit.

**Decision — `withings_tokens` is created directly in `whoop_tokens`' *current*, post-multi-tenancy shape: `user_id integer primary key references users(id)`, no surrogate `id` column, no singleton phase (DL-2026-08-26-a1).** Unlike Whoop, which was built single-user before the multi-tenancy convention existed and needed a dedicated later retrofit PRD (`migrations/1787083550593_whoop-multi-tenancy.js`, dropping `id smallint primary key default 1 check (id = 1)` and replacing it with `user_id` as the PK), there is no pre-existing Withings data to migrate away from — the table is created once, correctly, from the start. This makes the Withings migration strictly simpler than either Whoop migration it takes as a precedent: no backfill, no `PRIMARY_USER_EMAIL` resolution, no `pgStringLiteral()`-style raw-SQL-embedding workaround (the landmine documented in `migrations/1787083550593_whoop-multi-tenancy.js`'s own header comment, where `pgm.sql`'s `{param}` mustache templating quotes a plain string as an *identifier*, not a value — irrelevant here because this migration interpolates no runtime values at all).

**Decision — metric scope is exactly the three metrics that already have Fitdays parity and a dashboard consumer: `weight` (Withings measure type 1), `body_fat_pct` (type 6, "Fat Ratio"), `lean_body_mass` (type 5, "Fat Free Mass").** No other Withings biomarker (muscle mass, bone mass, water mass, segmental composition, visceral fat, vascular age, pulse wave velocity) is ingested — none has a dashboard consumer today, and adding them now would be scope creep past what a thin slice needs. **BMI is excluded entirely (DL-2026-08-26-a3)** — Withings' API has no native BMI measure type (only height + weight), and `bmi` isn't on the dashboard regardless (`lib/dashboard/types.ts`'s `DASHBOARD_METRICS` omits it).

**Decision — units are stored exactly as Withings sends them (kg), never converted at ingest.** This corrects an assumption from this slice's own planning discussion, where an ingest-time kg→lb conversion was initially thought necessary. It is not: `lib/dashboard/units.ts#toPounds` already exists precisely for this — "the dashboard shows weight and lean body mass in lb regardless of stored source units... conversion happens here at read/render time only" — and its own comment already anticipates a `unit === "kg"` source (`LB_PER_KG` conversion, currently dead code because no live source sends kg yet). Storing Withings' native `kg` unit is not just permitted but is the mechanism this function was built for, and it keeps the unified-schema convention ("unit stored exactly as sent, never converted," `README.md`) intact rather than making Withings the first source to violate it. `lib/dashboard/units.ts` itself is **not modified by this slice** — its `toPounds` logic already handles the case; this fact only matters for the *next* slice (the dashboard fast-follow), and is recorded here so that slice's author doesn't have to re-derive it.

**Decision — no `withings_workouts`-shaped second table.** `whoop_workouts` exists because a day can hold several Whoop workouts, which the `(source, metric, reading_date)` one-row-per-day shape of `biometric_readings` can't represent. Withings body-composition readings are daily scalars — at most one meaningfully "current" value per metric per day, exactly like Fitdays' shape — so they land directly in `biometric_readings`, no new table needed.

**Decision — the 1-year backfill triggers automatically inside the OAuth callback, not as a separate manual step (DL-2026-08-26-a4), and must not block the callback's redirect or risk Vercel's function-duration limit.** The callback route completes fast (as it does for Whoop today — a single token exchange), redirects the user to `/status` immediately, and separately triggers the backfill as a server-to-server call into the same sync mechanism the daily cron uses, with a wide date-range override, targeting `https://${process.env.VERCEL_URL}` when running on Vercel (production or Preview alike — `VERCEL_URL` is Vercel's own per-deployment hostname, always correct for the deployment actually executing the callback) and falling back to `NEXT_PUBLIC_APP_URL` only when `VERCEL_URL` is unset (local dev). **Never derive this target from `NEXT_PUBLIC_APP_URL` alone** — that value is pinned to `https://jerkai.app` in every environment specifically so Whoop's OAuth `redirect_uri` byte-matches its Dashboard registration (`lib/whoop-oauth.ts#redirectUri`), and reusing it here would send a Preview-environment first connect's backfill request to production's `/api/withings/sync` instead of the deployment that actually holds the new `withings_tokens` row — mirroring the exact pattern Whoop's own sync route already supports (`app/api/whoop/sync/route.ts`'s `resolveWindow`, which already accepts `?start=&end=` for "how the historical backfill runs: chunked date ranges... safe to re-run over any overlapping range," per that file's own header comment). This reuses proven infrastructure rather than inventing a new async job mechanism (this repo has no queue). **The mechanism for firing this trigger after the redirect is sent, without blocking it or risking Vercel's function-duration limit, is Next.js's `after()` (imported from `next/server`) — not a bare unawaited `fetch()`, which is not guaranteed to complete once the response has been returned on Vercel's serverless runtime (NFR-109). The build agent confirms `after()`'s availability and exact import path against this repo's installed Next version before relying on it.** **`app/api/whoop/sync/route.ts`'s own header comment documents Whoop's historical backfill as chunked ~90-day windows specifically to stay inside Vercel's function-duration limit — `after()` defers work past the response but does not extend that duration budget (confirmed against the installed Next version's own `after()` documentation). This slice's backfill follows the same discipline: `app/api/withings/sync/route.ts` declares an explicit `maxDuration` (mirroring Whoop's own `export const maxDuration = 60`, confirmed against the project's Vercel plan tier), and if the confirmed `measure/getmeas` pagination count for 365 days of data at NFR-101's rate cap would not complete inside that budget, the backfill chunks into sequential ~90-day windows rather than firing one unbounded call (NFR-101).**

**Decision — rate-limit safety is a stated property, not a fabricated mechanism, because this session cannot verify Withings' `getmeas` pagination contract byte-for-byte.** This planning session's own research (developer.withings.com) found a documented 120 requests/minute cap and confirmed the free "Basic Biomarker Pack" tier covers `weight`/`body_fat_pct`/`lean_body_mass` at zero cost, but did **not** verify from source whether one year of daily readings returns in a single `getmeas` call or requires pagination — Withings' own docs site is JS-rendered and this session's browser tooling could not reliably extract that specific page. §5's NFR-101/NFR-104 require the build agent to confirm the actual contract against Withings' live API reference before writing `lib/withings-api.ts`, the same "confirm live, never assume" discipline this project already applies to Postgres constraint names (`NFR-72`/`NFR-82`, prior slices) and to `node-pg-migrate`'s templating semantics (the `NFR-81` correction in `migrations/1787083550593_whoop-multi-tenancy.js`'s own header comment).

**What this slice is NOT:** no dashboard UI change of any kind — `lib/dashboard/types.ts`'s `DASHBOARD_METRICS` (byte-vendored into the sibling `jerkai-mcp` repo, per `docs/codebase.md`) is untouched, so this slice needs no `jerkai-mcp` re-vendor step either; no BMI; no muscle/bone/water mass or any premium/segmental/cardiovascular Withings metric; no friend-onboarding/`ALLOWLISTED_EMAILS` change; no Fitdays/Health Auto Export change; no disconnect/revoke feature; no admin UI.

## 2. Problem statement

Friends being onboarded next use a Withings smart scale, not Fitdays/Apple Health — and JerkAI has no way to ingest Withings data at all today. The three scale-sourced dashboard metrics (`weight`, `body_fat_pct`, `lean_body_mass`) have exactly one hardcoded source (Fitdays), reachable only through a single-secret, Albert-only webhook with no per-user concept.

## 3. Objective

Any signed-in user can connect their own Withings account via OAuth; a daily cron pulls and attributes fresh data correctly for every connected user independently (one user's failure never blocks another's, mirroring Whoop); and a newly connected user's trailing year of history backfills automatically, without exceeding Withings' published rate limits. Success = a connected user's `weight`/`body_fat_pct`/`lean_body_mass` rows land in `biometric_readings` with `source = 'withings'`, visible on their own `/status` page, ready for the dashboard fast-follow to surface — with zero risk of one user's Withings connection or data touching another's.

## 4. Functional Requirements — user-centered acceptance criteria

Written as testable Given/When/Then. New id prefix **AC-WS** (Withings smart-scale), numbered from 1 — no collision with any existing jerkai prefix (`AB`, `AU`, `D`, `FT`, `M`, `MU`, `N`, `PD`, `PM`, `PUE`, `ST`, `W`, `WT`), verified against every jerkai Build PRD in the vault and every jerkai test file this session. (Correction: an earlier pass of this list wrongly included `CV`, `DM`, `MF` — these are jerkai-mcp-only prefixes, a separate repo with its own AC namespace — and `QT`, a retired prefix with no live jerkai ACs. ### 4.1 Connect, reconnect, and per-user isolation

* **AC-WS1 (bare case)** — Given zero rows in `withings_tokens` (nobody has ever connected), When the cron sync runs, Then it completes successfully having processed zero users, writes no `biometric_readings` rows, records no misleading failure, and sends no alert.
* **AC-WS2** — Given a signed-in user completes the Withings OAuth connect flow for the first time, Then `withings_tokens` gains exactly one row for their `user_id`, with both tokens stored only in their AES-256-GCM-encrypted form (never plaintext).
* **AC-WS3** — Given two users each with their own connected `withings_tokens` row, When the cron sync runs, Then each user's pulled `biometric_readings` rows are attributed to their own `user_id` — never crossed, even where both users have a reading for the identical metric and date.
* **AC-WS4 (failure isolation)** — Given two connected users where one user's Withings API call fails (token refresh error, API outage) during a run, Then the other connected user's sync still completes, is recorded as its own independent outcome, and is not marked failed because of the first user's error.
* **AC-WS5 (connect/callback binding)** — Given user A initiates `/api/withings/connect` (setting both the state and user-id cookies) and, before the callback completes, the active session in that same browser becomes user B's, When Withings' redirect reaches `/api/withings/callback`, Then the callback is refused (same shape as a state mismatch — restart from `/api/withings/connect`) rather than attributing the resulting tokens to user B.
* **AC-WS6** — Given a user who already has a connected `withings_tokens` row, When they complete the connect flow again (re-consent/reconnect), Then their existing row is updated in place (same `user_id`), never duplicated.
* **AC-WS7** — Given a signed-in user with no `withings_tokens` row, When `getFreshAccessToken(userId)` is called for their id, Then it returns `null`.
* **AC-WS20 (bare case, session-gate exclusion)** — Given an unauthenticated request (no session cookie, no bearer token) reaches `proxy.ts`'s matcher for either `/api/withings/callback` or `/api/withings/sync`, Then it is passed through to the route handler rather than redirected to `/signin` — mirroring the existing exact-match exemptions for `api/whoop/callback$`/`api/whoop/sync$` (NFR-108).

### 4.2 Historical backfill (rate-limit safe)

* **AC-WS8** — Given a user completes the Withings OAuth connect flow for the **first time** (no pre-existing `withings_tokens` row before this connect), When the callback completes, Then a backfill covering the trailing 365 days is triggered automatically (§0), and resulting rows land in `biometric_readings` with `source = 'withings'` for `weight`/`body_fat_pct`/`lean_body_mass` wherever Withings has data in that window.
* **AC-WS9 (rate-limit safety)** — Given the 1-year backfill requires more Withings API requests than fit comfortably inside Withings' documented rate window, When the backfill executes, Then it never exceeds a fixed, conservative fraction of the documented per-minute cap (NFR-101) and honors any 429/rate-limit response the same way `lib/whoop-api.ts#apiGet` already does for Whoop (bounded retry, honoring the advertised reset delay) — rather than firing every request immediately and risking a hard failure mid-backfill.
* **AC-WS10 (reconnect does not re-backfill)** — Given a user who already has a `withings_tokens` row (reconnecting, AC-WS6), When the callback completes, Then no backfill is triggered — only the normal token update happens, so a routine reconnect never re-consumes a year's worth of rate-limit budget.

### 4.3 Daily sync & observability

* **AC-WS11** — Given the daily cron sync runs, When it pulls data for each connected user, Then it re-upserts a fixed trailing window (not a full-year re-backfill) uniformly across all connected users in that run — sized generously enough to cover a routine missed- or doubled cron run, mirroring `resolveWindow`'s default — and idempotently heals any gap up to that window via `upsertReading`'s per-(`user_id`, `source`, `metric`, `reading_date`) upsert.
* **AC-WS12** — Given a cron run covering two connected users, Then `sync_runs` gains one row per user for that run, `source = 'withings'` — never one row conflating both users' outcomes.
* **AC-WS13** — Given a signed-in user with a connected Withings account, When they load `/status`, Then they see their own Withings sync history (last successful sync, last run status) — achieved by adding `"withings"` to `lib/sources.ts#ACTIVE_SYNC_SOURCES`, with no other change to `app/status/page.tsx` (§1).
* **AC-WS14** — Given a connected user's sync fails, When the failure alert is sent, Then its body names that user (by email), matching the pattern `app/api/whoop/sync/route.ts#userSyncFailed`/`syncOneUser` already establish for Whoop.

### 4.4 Data fidelity, scope boundaries, and schema

* **AC-WS15 (units, unconverted)** — Given a Withings `weight` or `lean_body_mass` reading arrives in kg, When it is written to `biometric_readings`, Then its `unit` column is stored as `"kg"` exactly as received — never converted to lb at ingest time (§0).
* **AC-WS16 (BMI excluded)** — Given any Withings-sourced user's mapped readings, Then no `bmi` metric row is ever written for `source = 'withings'` (DL-2026-08-26-a3) — Withings measure type 1 (weight) and type 5/6 (fat-free mass/fat ratio) are mapped; no other measure type is mapped or stored.
* **AC-WS17 (device-local day resolution)** — Given a Withings measurement group with its own UTC timestamp, When it is mapped to a `biometric_readings` row, Then `reading_date` is the user's device-local calendar day for that timestamp (the same "shared date key" convention every other source in this app follows) — never the server's UTC day and never guessed when the required timezone information is unavailable (NFR-107).
* **AC-WS18 (migration, `biometric_readings`)** — Given the production migration runs, Then `'withings'` becomes an accepted value in `biometric_readings_source_check` without modifying, dropping, or reordering any pre-existing row.
* **AC-WS19 (migration, `sync_runs`)** — Given the production migration runs, Then `'withings'` becomes an accepted value in `sync_runs_source_check`, under the same no-pre-existing-row-touched guarantee as AC-WS18.

All prior NFRs remain in force; the following are additive, continuing jerkai's numeric series after **NFR-97** (current live high-water mark). * **NFR-98 — Every query over `withings_tokens` is scoped by `user_id`, enumerated by construction (not an unstated property):** the new `lib/withings-oauth.ts`'s `saveTokens`/`loadTokens`/`getFreshAccessToken` (all `where`/`values` clauses); its `listConnectedUsers` query (the cron loop's iteration source and AC-WS14's alert-email source); `app/api/withings/sync/route.ts`'s per-user loop and its two `recordSyncRun` call sites (success/partial and failure paths, mirroring `app/api/whoop/sync/route.ts`'s `syncOneUser`/`userSyncFailed`); and the callback route's first-connect-vs-reconnect check (§1, backs AC-WS8/AC-WS10) — implemented as a single atomic `insert ... on conflict (user_id) do update ... returning (xmax = 0) as inserted` against `withings_tokens`, not a separate SELECT-then-upsert, so the first-connect determination is atomic with the write and race-free. Any additional site touching `withings_tokens` discovered during build is added to this list before the PR, not scoped silently (mirrors NFR-77's own discipline).
* **NFR-99 — The connect→callback roundtrip attributes tokens only to the session that initiated it**, verified by comparing a second httpOnly cookie (`withings_oauth_user`) set at connect time against the callback's own fresh `session.user.id`, not merely by re-checking that *some* session exists at callback time (mirrors NFR-78; backs AC-WS5).
* **NFR-100 — The cron sync loop isolates per-user failures**: one connected user's error (token refresh, Withings API call, a bad record) never aborts, blocks, or misattributes another connected user's sync in the same run (mirrors NFR-79; backs AC-WS4).
* **NFR-101 — The 1-year backfill never exceeds half of Withings' documented per-minute request-rate cap (i.e., never issues more than 60 requests in any rolling 60-second window)**, and honors any 429/rate-limit response with a bounded retry against the advertised reset delay, mirroring `lib/whoop-api.ts#apiGet`'s existing one-retry-on-429 pattern (backs AC-WS9). **The exact numbers here (published cap, response header names, whether one year of `getmeas` data requires pagination at all) are this planning session's own external research and are not repo-verified facts — confirm against `developer.withings.com/api-reference`'s live `measure/getmeas` documentation before writing `lib/withings-api.ts`, and correct this NFR's stated cap if the live docs disagree (§0). If the confirmed `getmeas` pagination count for the trailing 365 days would not complete within `app/api/withings/sync/route.ts`'s declared `maxDuration` at this rate cap, the backfill chunks into sequential windows of no more than ~90 days each — mirroring `app/api/whoop/sync/route.ts`'s own historical-backfill chunking precedent — rather than firing one unbounded call (§0).**
* **NFR-102 — Units are stored exactly as Withings' API returns them, never converted at ingest** (§0; backs AC-WS15) — matches the unified-schema convention already documented for Fitdays (`migrations/1784053997735_widen-sync-runs-source-apple-health.js`'s column comments: "Unit exactly as sent... never converted").
* **NFR-103 — Withings OAuth tokens are encrypted at rest via AES-256-GCM under a dedicated `WITHINGS_TOKEN_ENCRYPTION_KEY`, distinct from `WHOOP_TOKEN_ENCRYPTION_KEY`** — a new, self-contained `lib/withings-crypto.ts` mirroring `lib/whoop-crypto.ts`'s shape, not a shared/generalized module (§1) — so either integration's key can be rotated independently and `lib/whoop-crypto.ts` stays outside this slice's file budget.
* **NFR-104 — Withings' OAuth token-response field names and measure-type ids (1 = weight, 5 = fat-free mass, 6 = fat ratio) are confirmed against Withings' own live API reference at implementation time, never assumed from this PRD's own research** (§0/§1) — mirrors this project's own "confirm live, never assume" discipline already applied to Postgres constraint names (`NFR-72`/`NFR-82`) and to `node-pg-migrate`'s templating semantics (the correction documented in `migrations/1787083550593_whoop-multi-tenancy.js`'s own header comment). This planning session's own live verification (2026-08-26) found Withings wraps its token response in a `{status, body}` envelope, not a flat RFC 6749 response like Whoop's — the build agent re-confirms this against Withings' live API reference before implementing `lib/withings-oauth.ts`'s token-exchange functions, and does not assume the envelope shape carries through unverified either.
* **NFR-105 — A reconnect never re-triggers the 1-year backfill** — the callback distinguishes "first-ever connect" from "reconnect" by checking for a pre-existing `withings_tokens` row *before* `saveTokens` runs, and only a true first connect enqueues the backfill (§0; backs AC-WS10).
* **NFR-106 — No `withings_workouts`-shaped second table exists.** Withings body-composition readings are daily scalars and land directly in `biometric_readings`, structurally distinguishing this integration's data model from Whoop's (which needed `whoop_workouts` because multiple workouts can occur in one day, which the tall one-row-per-day shape cannot represent) (§0).
* **NFR-107 — The device-local calendar day for a Withings reading is never guessed.** If Withings' `getmeas` response does not carry per-measurement-group timezone information sufficient to compute the user's local day (unlike Whoop's API, which supplies `timezone_offset` per record, consumed by `lib/whoop-map.ts#localDay`), the build agent stops and flags this to Albert rather than defaulting to UTC or inferring from server time — the same "never guess, fail loudly" discipline this project already applies elsewhere (e.g. the zero-vs-multiple-candidate-owner precondition in `migrations/1786637399180_...js`) (backs AC-WS17).
* **NFR-108 — `proxy.ts`'s matcher exempts `/api/withings/callback` and `/api/withings/sync` from the session-gate redirect, by exact-match path, mirroring its existing `api/whoop/callback$`/`api/whoop/sync$` exemptions.** Without this, an unauthenticated request to either route (Withings' own OAuth redirect; Vercel Cron's bearer-authorized call) is redirected to `/signin` before it ever reaches the route handler's own auth check, making both routes unreachable in production regardless of how correctly they're otherwise implemented (backs AC-WS20).
* **NFR-109 — The callback route's post-redirect backfill trigger (§0/OQ-1) is scheduled via Next.js's `after()` (from `next/server`), never a bare unawaited `fetch()`.** An unawaited call has no guarantee of completing once the response has been sent on Vercel's serverless runtime; `after()` is the framework-provided mechanism for exactly this "do more work after responding" case. The build agent confirms `after()`'s exact import path and availability against this repo's installed Next version before relying on it (backs AC-WS8, §0). **The internal call `after()` schedules targets `https://${process.env.VERCEL_URL}` (falling back to `NEXT_PUBLIC_APP_URL` only when `VERCEL_URL` is unset, i.e. local dev) — never `NEXT_PUBLIC_APP_URL` alone, which is pinned to `https://jerkai.app` in every environment for Whoop's OAuth `redirect_uri` byte-match and would misroute a Preview-environment backfill to production's `/api/withings/sync`.** AC-WS8(c)'s manual verification step additionally confirms, via response headers or logs, that the backfill's internal call actually lands on the same deployment that issued it — checked in Preview, not only in production.
