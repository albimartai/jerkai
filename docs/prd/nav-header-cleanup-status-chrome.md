## 0. Scope & Sequencing Note (read first)

`app/ui/nav-header.tsx` renders the shared header on every gated page except one. Read directly (2026-08-19): the live-variant "Log Meal" link is `<Link href="/log-meal" className="rounded-md border border-zinc-200 px-3 py-1 text-sm text-zinc-600 hover:bg-zinc-50 dark:border-zinc-800 dark:text-zinc-300 dark:hover:bg-zinc-900">+ Log meal</Link>` and the "Status" link carries the identical bordered className with the text "Status". Both were written this way when the CTA first shipped and have not been revisited since. Albert wants the leading "+" dropped, "Meal" capitalized, and the border removed from both links — three small, purely cosmetic edits confined to one file.

The fourth item is not cosmetic. `app/status/page.tsx`, read directly (2026-08-19), does not import or render `NavHeader` at all — it returns a bare `<main>` with only an `<h1>Sync status</h1>` and the per-source sync rows. Every other gated route (`/`, `/weekly`, `/daily`, `/log-meal`, `/settings/targets`) renders the shared header; `/status` alone drops it entirely, so a user who clicks "Status" loses the "JerkAI" wordmark and every other nav link and has to use the browser back button to get back into the app. `docs/context.md` states "Every page header carries Weekly/Daily nav plus Status (unchanged, AC-D15)" — but AC-D15 itself (`docs/prd/archive/v1-dashboard.md`, read directly 2026-08-19: "Given the user clicks Status, Then the existing `/status` sync-health page opens") only ever asserted that the *link* works, never that `/status` itself keeps the header once opened. So this is not a regression against a broken AC — it is a gap the existing AC series never covered, present since `/status` shipped in v1. This slice closes it by giving `/status` the same `NavHeader` treatment every other gated page already has, matching neither Weekly nor Daily as active — the same convention `/log-meal` and `/settings/targets` already use (`app/ui/nav-header.tsx`'s own comment: "`active` is undefined on pages outside the Weekly/Daily resolution pair").

**Decision — bundle the CTA text/border cleanup and the Status-page header fix into one slice, not two (decision, not yet logged — flag for `decision-log` once Albert confirms).** Considered: (A) one slice covering all four changes, since three live in `nav-header.tsx` and the fourth is a one-line consumer of that same component, all reviewed together as "header polish"; (B) two slices — cosmetic text/border changes in one PR, the Status-page structural fix in another, on the theory that a pure-CSS change and a markup-structure change are different kinds of risk. Rejected B: the fourth change's own diff is a single `NavHeader` import + wrap, no different in size or risk from the CTA text/border edits, and splitting would mean re-reading and re-branching from the same one-file component twice for no isolation benefit — nothing in (B) can ship or fail independently of (A). Build A.

**Decision — `/status` gets `active={undefined}` (no highlighted resolution link), not a new "status" active state (decision, not yet logged).** Considered: (A) leave `active` unset, matching the existing convention for `/log-meal` and `/settings/targets`; (B) widen `NavHeader`'s `active` prop type to include `"status"` and highlight the Status link when on that page. Rejected B: `NavHeader`'s `active` prop is explicitly typed to the Weekly/Daily resolution pair (`app/ui/nav-header.tsx`'s own comment: "widening it would change the shared live path too") and no other non-resolution page (`/log-meal`, `/settings/targets`) gets a highlighted state today — introducing one only for `/status` would be a new, unrequested visual convention, not what Albert asked for. Build A.

What this slice is NOT: not a redesign of the header's visual style beyond the three named edits (no new colors, no new spacing, no new icons); not a change to the demo (`variant="demo"`) header, which keeps its About link and its own unbordered link styling untouched; not a change to what `/status` queries, computes, or displays (see the companion "Status Sync Times — Local Timezone" PRD for that); not a change to `/status`'s `auth()` redirect-to-signin behavior.

## 2. Problem statement

Three small visual inconsistencies and one structural gap, all in the shared header:

1. The live-variant "Log Meal" link reads "+ Log meal" — a leading "+" Albert wants dropped and a lowercase "meal" he wants capitalized to "Meal".
2. The live-variant "Log Meal" and "Status" links each render with a visible 1px border (`border border-zinc-200 dark:border-zinc-800`) that the adjacent "Targets" link does not have — Albert wants that border removed from both.
3. `app/status/page.tsx` renders no header at all: no "JerkAI" wordmark, no Weekly/Daily/Targets/Log Meal/Status nav. A user who navigates to `/status` — by clicking the header's own "Status" link, or by direct URL — lands on a page with no way back into the app except the browser's back button.

## 3. Objective

The header reads "Log Meal" (no "+", "Meal" capitalized) with no border on either the Log Meal or Status link, and `/status` renders the identical shared header every other gated page renders, with neither Weekly nor Daily marked active. Success = a signed-in user can navigate `/weekly` → click "Status" → see the same "JerkAI" wordmark and full nav bar on `/status` that they saw on `/weekly`, and the Log Meal/Status links read as flat text-style links with no visible outline.
