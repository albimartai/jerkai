## 0. Scope & Sequencing Note (read first)

`app/status/page.tsx` (re-read 2026-08-24 — now 72 lines, post-Nav-Header-Cleanup; the query below is at lines 29–39) queries `sync_runs` with:

```sql
select source,
       to_char(max(coalesce(finished_at, started_at)) filter (where status = 'success')
               at time zone 'utc', 'YYYY-MM-DD HH24:MI "UTC"') as last_success,
       to_char(max(coalesce(finished_at, started_at))
               at time zone 'utc', 'YYYY-MM-DD HH24:MI "UTC"') as last_run_at,
       ...
```

Both `to_char(... at time zone 'utc', ...)` calls do the timezone conversion and the string formatting inside SQL, on the server, baking in a fixed "UTC" label no matter who's looking at the page or where they are. `started_at`/`finished_at` are `timestamptz not null default now()` / `timestamptz` respectively (`migrations/1783612708598_create-sync-runs.js`, read directly 2026-08-19) — genuine, unambiguous UTC instants under the hood; the "UTC" that shows up on screen today is a formatting choice in the query, not a property of the stored data. Albert wants the displayed time to match his device's own timezone instead — i.e., the browser/OS's local timezone, whatever that happens to be, not a second hardcoded zone swapped in for the first.

A Next.js Server Component (which `Status` is, per its `export default async function Status()` shape with no `"use client"` directive) runs on the server and has no way to know the visitor's device timezone at render time — Vercel's server clock and timezone are not the viewer's. This exact problem already exists elsewhere in this codebase and already has an established solution: `app/ui/log-meal-form.tsx`'s `todayLocal()` (read directly, 2026-08-19, lines 24–33) computes "today" using `new Date()` with no explicit timezone, and its own comment states the reason plainly: *"Vercel's server clock is UTC, so computing 'today'... during server render would misclassify evenings against the device's actual local time"* (NFR-2). `todayLocal()` is deliberately client-only, and its caller (`app/ui/log-meal-panel.tsx`, `AC-M31`) renders `null` for one mount tick rather than guess a value server-side, then fills it in once the client knows its own clock. This slice follows that same shape for time-of-day display rather than a calendar day: the server hands the client a raw, unconverted UTC instant, and a client-side piece of code — not SQL, not the server — turns it into a locale/timezone-aware string using the browser's own default timezone resolution (i.e., calling `Date`/`Intl` formatting methods with no explicit `timeZone` override, the same "let the runtime decide" approach `todayLocal()` already relies on).

**Decision — move timezone conversion and string formatting out of SQL entirely; the server passes a raw ISO instant, a Client Component formats it (decision, not yet logged — flag for `decision-log` once Albert confirms).** Considered: (A) drop `to_char(... at time zone 'utc', ...)` from the query, select the raw `timestamptz` columns (the Neon driver returns these as ISO 8601 strings or `Date` objects), and format them client-side; (B) keep the SQL formatting but add a second, client-computed offset and do string math in the browser to convert an already-UTC-labeled string; (C) detect the visitor's timezone server-side via a request header (e.g., a client-set cookie) and pass an explicit IANA zone name into a still-server-side `to_char(... at time zone $1, ...)`. Rejected B: re-parsing an already-formatted "YYYY-MM-DD HH24:MI UTC" string in the browser to re-convert it is strictly more fragile than just not throwing away the raw instant in the first place — two formatting passes instead of one, and a second place a bug can hide. Rejected C: no such cookie or header exists anywhere in this codebase today (confirmed via read of `app/status/page.tsx`, `proxy.ts`, and `auth.ts`), and inventing one is real new machinery for a problem the app has already solved a simpler way (`todayLocal()`) — a request header also can't distinguish "visitor's timezone" from "server's guess," which is exactly the discriminability problem `todayLocal()`'s own comment exists to avoid. Build A.

What this slice is NOT: not a change to which `sync_runs` rows are queried or how they're scoped per user (AC-WT8, shipped, untouched); not a change to the `"never"` fallback text for a source with no successful sync (that string carries no timezone and is unaffected); not a schema change (`sync_runs`' columns are already `timestamptz`, exactly what this slice needs); not the nav-header wrapping of `/status` — that companion PRD ("Nav Header Cleanup & Status Page Chrome") has already shipped (built 2026-08-20, merged main via PR #28 on 2026-08-21); `/status` already renders the shared `NavHeader` inside the standard `mx-auto w-full max-w-3xl px-4 pb-10 font-sans` `<main>` wrapper. This slice's diff is scoped entirely inside that already-wrapped markup and does not touch the header or the `<main>` wrapper itself.

## 2. Problem statement

`app/status/page.tsx`'s SQL query formats both the "Last successful sync" and "Last run" timestamps as fixed UTC strings (`to_char(... at time zone 'utc', 'YYYY-MM-DD HH24:MI "UTC"')`) before they ever reach React. Every visitor sees the same UTC-labeled time regardless of their own device's timezone — for Albert, viewing from a non-UTC timezone, this means mentally converting every displayed sync time to know how recent it actually was, which is the opposite of what a status page is for.

## 3. Objective

`/status` displays "Last successful sync" and "Last run" times converted to the viewer's own device-local timezone — whatever that is — rather than a fixed UTC string. Success = a single testable condition: given a known `sync_runs` row with a specific UTC instant, rendering `/status` in a browser/test environment configured to a specific non-UTC timezone produces a displayed time that reflects that timezone's offset from the stored instant, not UTC and not whatever timezone the server process happens to run in.

## 4. Functional Requirements — user-centered acceptance criteria

"The user" = Albert (single user; multi-tenancy is live, but this slice's formatting behavior does not vary by user — only the underlying rows do, per the unmodified AC-WT8). New id prefix **AC-ST**, numbered from 1 — a new two-letter prefix avoiding collision with jerkai's existing series (`AB`, `AU`, `D`, `M`, `MF`, `MU`, `N`, `PD`, `PUE`, `QT`, `W`, `WT` — re-verified against `docs/codebase.md` §7 as of 2026-08-24, which also confirms jerkai-mcp keeps a wholly separate lettered NFR series and its own `AC-CV`/`AC-DM` prefixes that never share jerkai's numbering, and confirms the newly-shipped `AC-PM` (Preview Migration Gap Fix, PR #29, 4 ACs, all ops/manual checks) does not collide with `AC-ST` either; `/status` has never had a dedicated AC series of its own — its only prior citation is AC-D15, which governs the link that opens it, not what it displays).

### 4.1 Bare case — no successful sync yet

* AC-ST1 (bare case) — Given a source has never had a successful sync (`last_success` is null), When `/status` renders, Then it still shows the literal text `"never"` for that source's "Last successful sync" line — unchanged by this slice, since `"never"` is not a timestamp and carries no timezone.

### 4.2 Local-timezone display

* AC-ST2 — Given a source's last successful sync happened at a known UTC instant, When `/status` is rendered and viewed in a browser/runtime whose configured local timezone is something other than UTC (e.g., America/Chicago, UTC−5), Then the displayed "Last successful sync" time reflects that timezone's offset from the stored instant — not the literal UTC hour, and not a hardcoded "UTC" label.
* AC-ST3 — Given a source's most recent run did not succeed (`status` is `'failure'` or `'partial'`), When `/status` renders the "Last run: … at …" line for that source, Then that timestamp is displayed in the same viewer-local timezone as AC-ST2, by the same mechanism — no divergence in how the two timestamp displays resolve "local."

### 4.3 No regression to existing scoping and fallback behavior

* AC-ST4 (regression) — Given `tests/integration/status.test.ts`'s existing `AUTO-GENERATED TEST STUB` / `DO NOT EDIT` block (`AC-WT8`: per-user sync-history scoping, including its `"never"`-occurrences-equal-2 bare-case assertion), When this slice ships, Then that block's assertions pass unmodified — this slice changes how a non-null timestamp is displayed, not which rows are queried, how they're scoped per user, or the `"never"` fallback text.

## 5. Non-Functional Requirements (FDE)

All prior NFRs (1–97 shipped as of 2026-08-24, per `docs/codebase.md` §7: NFR-83–85 via Nav Header Cleanup & Status Page Chrome (PR #28, 2026-08-21); NFR-86–87 via Weekly Ledger Week Column Wrap (PR #30, 2026-08-24); NFR-94–97 via Preview Migration Gap Fix (PR #29, 2026-08-21)) remain in force where applicable; the following are additive, continuing from 88. An unrelated fifth PRD ("Preview Migration Gap Fix," NFR-94–97, prefix `AC-PM`) also shipped in the interim without affecting this PRD's own reservation. NFR-88–91, reserved by this PRD since 2026-08-19, remain uncollided — Preview Migration Gap Fix's own §5 explicitly preserves this reservation, and `docs/codebase.md` §7 confirms NFR-88–93 as "reserved, not shipped." No renumbering is needed.

* NFR-88 — **Timezone conversion and formatting happen only on the client, never in SQL or anywhere else on the server.** `app/status/page.tsx` (Server Component) selects and passes down a raw, unconverted UTC instant for each non-null timestamp (e.g., an ISO 8601 string via `.toISOString()`, or the raw `timestamptz` value the Neon driver returns) to a Client Component (`"use client"`), which owns all timezone conversion and display formatting. `app/status/page.tsx` itself performs no `to_char(...)`, no `at time zone`, and no other formatting of a non-null timestamp — the ordered path is: SQL returns a raw instant → the Server Component passes it through unmodified as a prop → the Client Component formats it. Failure mode this prevents: formatting anywhere on the server (as today's `at time zone 'utc'` does) bakes in a fixed zone that no client-side code can recover the original instant from without re-parsing a lossy, pre-formatted string (§0's rejected option B).
* NFR-89 — **The client-side formatting relies on the runtime's default timezone resolution, never a hardcoded IANA zone string.** Matches the established `todayLocal()` pattern (`app/ui/log-meal-form.tsx`, NFR-2): the formatting call passes no explicit `timeZone` option, so it resolves to whatever the browser/OS considers local — the same "let the runtime decide" property that makes `todayLocal()` correct for any device, not just Albert's. A build that hardcodes `"America/Chicago"` (or any other fixed zone) has swapped one wrong hardcoded zone for another and has not satisfied this NFR, even if it happens to look correct for Albert today.
* NFR-90 — **No permanent SSR/CSR mismatch and no lingering incorrect value.** If the server-rendered markup for a given timestamp differs from what the client renders after hydration (because the server cannot know the viewer's timezone), that difference resolves within the same render/hydration pass this app already uses for other device-local values (`todayLocal()`'s caller, `app/ui/log-meal-panel.tsx`, renders `null` for one mount tick rather than a wrong guess, per its own `AC-M31` comment) — it must not surface as a persistent wrong time, a React hydration-mismatch warning, or a value that only updates on a second interaction.
* NFR-91 — **The local-timezone behavior is verified against a timezone that provably differs from whatever the test runner's own ambient timezone happens to be, not assumed.** A test that merely renders the page and eyeballs a plausible-looking time cannot distinguish "correctly local" from "happens to match because CI runs UTC and the local zone is also UTC" (the same discriminability failure this project's own Definition of Ready calls out for deploy/request-time behavior — [[JerkAI - Definition of Ready & Done]], "Verification method known for anything CI cannot reach"). The test must force or observe a specific non-UTC zone as part of the assertion itself.
