## 0. Scope & Sequencing Note (read first)

JerkAI's sign-in gate (Auth.js magic-link, `proxy.ts` session check) currently allows exactly one email address to sign in at all: `lib/auth-callbacks.ts#signIn` compares the requested address against a single `ALLOWLISTED_EMAIL` env var and fails closed if it is unset (`lib/auth-callbacks.ts:16-27`, verified this session). Extending JerkAI to more than one person starts here, because every other multi-user slice — data isolation, per-user Whoop, per-user dashboard state — assumes more than one person can actually sign in.

**Decision — keep the existing auth stack; widen the allowlist to a list, not a table (DL-2026-08-07-a1).** Considered switching to a managed auth provider (Clerk, Supabase Auth, Auth0, WorkOS) for built-in invite flows and a user-management dashboard. Rejected: the magic-link flow already works, and a full auth migration buys nothing an allowlist of "a few close friends" needs. Considered a database-backed allowlist table for editability without a redeploy. Rejected for now: at this volume (a handful of friends, added rarely), the redeploy cost of an env-var change is lower than building and securing an admin surface. Build: `next-auth` v5 + Resend + Neon adapter + JWT session unchanged; `signIn`'s single-string equality becomes list membership, sourced from one hardcoded env var.

**Decision — this slice ships before data isolation exists, so its deployed allowlist may contain only Albert's own email (DL-2026-08-07-a2).** The companion slice "Multi-User Data Model Retrofit" (separate PRD, not yet authored) adds `user_id` to `biometric_readings`, `manual_macro_entries`, and `daily_targets`. Until that ships and its production migration is confirmed live, every row in those tables is unscoped — reachable by any session that passes the sign-in gate. **A second allowlisted email must not be added to the deployed `ALLOWLISTED_EMAILS` value in any environment until the data-isolation PRD is merged and its production migration is verified live.** This is a deployment-configuration constraint, not something this slice's code can enforce (there is no code path that knows whether the sibling PRD has shipped) — it is carried here as an explicit DoD/DoR item (§6) rather than left as a verbal agreement, per the same reasoning DL-2026-08-07-a2 records.

**Rename, not reuse.** The env var is renamed from `ALLOWLISTED_EMAIL` (singular) to `ALLOWLISTED_EMAILS` (plural). A singular-named var holding a comma-separated list is exactly the kind of ambiguity that causes an operator to misread what it does; the rename makes the plural shape visible at every place the var is referenced. **Operational consequence, called out because the check fails closed:** the deployed Vercel value must be renamed from `ALLOWLISTED_EMAIL` to `ALLOWLISTED_EMAILS` in every environment enforcing the gate (Production, Preview) at or before the deploy that carries this change goes live — the old var is no longer read by any code path, so if the new one is not set, **the fails-closed design denies every sign-in attempt, including Albert's own**, until it is set. This is not a hypothetical: it is the same class of deploy-time, env-dependent behavior [[JerkAI - Definition of Ready & Done]] already requires a named verification method for. See §5 NFR-66 and §6.

**What this slice is NOT:** no data isolation, no per-user Whoop or ingest changes, no dashboard changes, no `jerkai-mcp` changes, no `/demo` changes (that route calls no auth code at all and is unaffected by construction), no allowlist database table, no admin UI, and — operationally — no friend actually invited yet.

## 2. Problem statement

Exactly one email address can sign in to JerkAI today — the gate is a single-string equality check that has no way to name a second person. Every subsequent multi-user slice (data isolation, per-user Whoop, per-user dashboard state) requires that more than one address can pass the sign-in gate at all.

## 3. Objective

`lib/auth-callbacks.ts#signIn` accepts sign-in from any address present in a hardcoded, operator-managed list, while preserving every existing security property of the single-address check: fail-closed on missing/empty configuration, case-insensitive and whitespace-trimmed matching, and no default-allow path under any parsing outcome. Success = the mechanism is ready for a second address the moment the data-isolation slice ships, without having actually admitted one yet.

## 4. Functional Requirements — user-centered acceptance criteria

Written as testable Given/When/Then. "The gate" = `lib/auth-callbacks.ts#signIn`. New id prefix **AC-AU** (allowlist), numbered from 1 — no collision with `AC-D`, `AC-N`, `AC-W`, `AC-M`, `AC-PD`, or `AC-AB` (verified against every jerkai Build PRD in the vault this session; none uses `AC-AU`).

* **AC-AU1 (bare case)** — Given `ALLOWLISTED_EMAILS` is unset, empty, entirely whitespace, or parses to zero non-empty entries (including the case where only the old singular `ALLOWLISTED_EMAIL` is set — it is no longer read), When any address attempts to sign in, Then sign-in is denied for that address and an error is logged identifying `ALLOWLISTED_EMAILS` as having no usable entries — accurate for both the unset case and the set-but-parses-to-zero cases (empty, whitespace-only, or malformed-to-zero) — mirroring the existing fail-closed behavior (`lib/auth-callbacks.ts:23-24`), extended to the list form. A single fixed message covering both the unset and parses-to-zero cases (e.g., `"sign-in rejected: ALLOWLISTED_EMAILS has no usable entries"`) is sufficient and preferred over per-case message variants, to keep the assertion a simple `toHaveBeenCalledWith` rather than a substring match.
* **AC-AU2** — Given `ALLOWLISTED_EMAILS` contains exactly one address (Albert's own — the deployed state this slice ships with, per §0), When that address attempts to sign in, Then sign-in is allowed — the single-address case continues to work exactly as it does today.
* **AC-AU3** — Given `ALLOWLISTED_EMAILS` contains multiple addresses, When the signing-in address matches an entry that is not the first in the list, Then sign-in is allowed — the check is real list membership, not an accidental first-entry-only comparison.
* **AC-AU4** — Given `ALLOWLISTED_EMAILS` contains multiple addresses, When the signing-in address matches none of them, Then sign-in is denied.
* **AC-AU5** — Given `ALLOWLISTED_EMAILS` contains an entry with mixed case and/or surrounding whitespace (e.g. `" Friend@Example.COM ,other@x.com"`), When a signing-in address matches that entry case-insensitively and after trimming, Then sign-in is allowed — extending the existing single-value case/whitespace normalization (`lib/auth-callbacks.ts:16,22,27`) to every entry in the list, on both the list side and the submitted-address side.
* **AC-AU6** — Given `ALLOWLISTED_EMAILS` contains a malformed separator (a stray double comma or a trailing comma, e.g. `"a@x.com,,b@y.com"` or `"a@x.com,"`), When an address consisting of an empty string, or of only whitespace, is submitted, Then sign-in is denied in both cases — parsing must never produce an empty-string list entry that an empty or whitespace-only submitted address could match.
* **AC-AU7** — Given the `authorized` callback that drives `proxy.ts`'s session gate, Then its behavior is unchanged by this slice: it returns `false` with no session and `true` with any valid session, independent of the allowlist's representation (extends the existing tests in `lib/auth-callbacks.test.ts`'s `describe("authorized callback — session gate", ...)` block, lines 66-74).

## 5. Non-Functional Requirements (FDE)

All prior NFRs remain in force; the following are additive, continuing jerkai's numeric series after **NFR-62** (Demo About Surface — verified as the current high-water mark this session against every jerkai Build PRD in the vault). Note: an earlier `NFR-63`–`NFR-80` allocation exists under the `AC-QT*` id series in [[JerkAI - Build PRD - MCP Server Foundations & Metric Registry (Slice 1, shipped)]] (that repo's header blockquote); per that PRD, "the earlier `AC-QT*` / `NFR-63`–`NFR-80` allocation was never built and no longer resolves," so `NFR-63` below is a fresh allocation in the jerkai numeric series, not a collision.

* **NFR-63 — Fail-closed is an invariant of the widened check, not a case of it.** No parse outcome reachable by this slice's parsing (split on comma → trim each resulting entry → lowercase each entry → filter out empty entries) — unset, empty, whitespace-only, or malformed input that parses to zero or more entries — may ever result in "allow all" or "allow any non-empty string." A future change to the list format is a new slice's NFR, not covered here. The absence of a valid, non-empty allowlist entry matching the submitted address denies that address. State this as a property the implementation must hold, not a specific branch to code.
* **NFR-64 — No new persistence or admin surface.** This slice introduces no database table, no migration, no admin UI, and no runtime mutation path for the allowlist (DL-2026-08-07-a1). The allowlist remains exactly one env var, read at request time.
* **NFR-65 — Blast radius is one function and its env var.** `auth.ts`, `proxy.ts`, and `app/signin/page.tsx` are unchanged by this slice — verified this session to contain no reference to `ALLOWLISTED_EMAIL`/`ALLOWLISTED_EMAILS` outside `lib/auth-callbacks.ts`, `lib/auth-callbacks.test.ts`, and `.env.example`, among files git-tracks. (`.env.local` also holds the singular var locally — gitignored, untracked, and expected per `.env.example`'s own "copy to `.env.local`" instruction; it carries no code-diff risk and is out of scope for this claim.) The only production code touched is `signIn`'s function body in `lib/auth-callbacks.ts`; `auth.ts` already imports `signIn` and `authorized` by reference (`auth.ts:6`) and neither's signature changes.
* **NFR-66 — The deployed allowlist value is verified live, not assumed from the diff.** Before the deploy that carries this change is considered done, the actual `ALLOWLISTED_EMAILS` value in each Vercel environment that enforces the gate (Production, Preview) is checked by reading the actual value — either the Vercel dashboard's Project → Settings → Environment Variables detail view for `ALLOWLISTED_EMAILS` in each environment (not just confirming the name is listed), or `vercel env pull .env.vercel-check --environment=production` (and the Preview equivalent) followed by inspecting the pulled value; `vercel env ls` alone is insufficient — it prints variable names, not values — not against `.env.example`, not against this PR's diff, and not from memory — and confirmed to contain Albert's email and no other address. This is a configuration claim in the sense [[JerkAI - Build Failure Ledger]] FM-01 describes: not writable as "done" without a query against the live system. This check is human-performed (Albert has the Vercel credential; it is not shared into an agent session, mirroring the existing production-migration DoD pattern) and is required precisely because the rename means an unset new var fails closed for everyone, including Albert.
