## 0. Scope & Sequencing Note (read first)

### 0.1 Why this slice, why now

Albert wants the page currently labeled "Weekly" (`/weekly`) relabeled "Results" — the nav-adjacent label and the route both change, matching how the label reads more accurately as a scorecard of weekly outcomes (five columns of deltas/states, "how did my weeks go") rather than just naming the time grain. This is a pure rename: no change to what the page shows, how it computes its rows, or how drill-down into `/daily` works.

The only prior full page-rename in this repo is [[JerkAI - Build PRD - Rename Data Page to Connect]] (`/data` → `/connect`), and this slice follows its conventions closely: relocate the route directory with `git mv`, rename the page's own exported function, update the nav label, and groom every stale test/doc reference — split precisely into **value edits** (an assertion would otherwise fail) and **name grooms** (the assertion still passes, but the description now reads wrong). Confirmed live this session via an exhaustive repo-wide grep of both `/weekly` and `Weekly`: every occurrence outside `app/weekly/`, `app/demo/weekly/`, and the nav/label code is either (a) a reference to the `WeeklyLedger` component or its supporting `lib/dashboard/` functions — which this slice does **not** rename, because "weekly" there accurately describes ISO-week-grain data, not the page's display identity — or (b) a route/label reference this slice's own §1 enumerates precisely.

Four scope decisions were made directly with Albert this session, before any drafting, because they diverge from established repo precedent or from an assumption a build agent might otherwise default to:

**Decision — `/weekly` and `/demo/weekly` are hard-removed, not redirected (Albert's explicit direction, 2026-09-11, deviating from established convention).** Considered: (A) a single-hop `redirect("/results")` stub at `/weekly`, matching every prior rename in this repo (the original strip-dashboard route → `/daily` per `AC-W8`; `/status` → `/data` → `/connect` per the Connect rename's own `NFR-131`, "every legacy path reaches the current route in exactly one redirect"); (B) hard removal — no stub file at all, so a request to `/weekly` gets Next's ordinary 404 for a route that does not exist. Albert confirmed (B) explicitly, having been shown that every precedent in this repo uses (A). This is a genuine, first-of-its-kind deviation, called out here so a future session does not read "no redirect" as an oversight. Build (B). An old bookmark/external link to `/weekly` gets whatever `proxy.ts`'s existing gate already gives any nonexistent gated path today: signed out, a redirect to `/signin`; signed in, a genuine 404 the moment this ships (§0.2) — flagged, not softened.

**Decision — the public demo surface is in scope (Albert's explicit direction).** Considered: (A) live app only, leaving `/demo/weekly` and the demo About page's "Weekly" list item unrenamed until a separate fast-follow; (B) rename both surfaces in the same slice, so the live app and the public-facing demo agree. Albert chose (B) — matching this repo's own standing lesson against deferred staleness ([[JerkAI - Build Failure Ledger]] `FM-23`: "this PRD's own §1/§6 defers `docs/codebase.md`'s pre-existing staleness with a boilerplate 'flagged, not fixed' clause... one slice after *Footer Privacy Link* proved the in-scope fix achievable"). Build (B): `app/demo/weekly/` relocates to `app/demo/results/`, `proxy.ts`'s `DEMO_HOST` rewrite target changes, and the About page's copy changes.

**Decision — "page title" means the nav-header label text, not a new browser-tab `<title>` (Albert's explicit confirmation).** Confirmed live this session (mirroring the Connect PRD's own §0.1 finding): no gated page in this app declares `export const metadata` today — only `app/privacy/page.tsx`, `app/demo/layout.tsx`, and `app/demo/about/page.tsx` do, and none references "/weekly" or "Weekly" in any form. Adding a per-route title to `/results` would be new scope, not a rename. Albert confirmed nav-label-only. Build accordingly — no `metadata` export is added.

**Decision — stale test/describe names inside `DO NOT EDIT` blocks are groomed, not just value-edited (Albert's explicit direction, matching the Connect rename's own expanded scope, its §0.3).** Every describe/it string that names the old route or label as prose — not just the assertions that would otherwise fail — is corrected. §1 enumerates every value edit and every name groom precisely, by file and line, so the diff stays exactly as large as the rename requires and no larger.

What this slice is NOT: no change to `/daily` or its "Daily" label; no change to the ledger's rows/columns/deltas/states/drill-down math or rendering (`WeeklyLedger`, `buildWeeklyView`, `buildWeeklyLedger`, `weeklyStallBadge` all byte-unchanged, §5 NFR-152); no new browser-tab `<title>`; no edit to the archived predecessor PRD `docs/prd/archive/weekly-ledger.md` (historical record — the Connect PRD established this precedent by never editing its own predecessor's archived text, only citations of it elsewhere, §8 OQ-5); no schema change, no migration.

### 0.2 What "hard removal" actually requires, mechanically

Because `/weekly` is not becoming a redirect stub, there is no new `app/weekly/page.tsx` to write after the move — `git mv app/weekly app/results` (and `git mv app/demo/weekly app/demo/results`) leaves nothing behind at the old paths. The only code-level assertion this produces is a negative one (the route no longer exists) plus the one real behavior change every hard-removal touches: `app/page.tsx`'s import of `WEEKLY_LEDGER_WINDOW_DAYS` must follow the file to its new path, or the build fails at compile time (not silently) — confirmed live this session that this is genuinely a compile error, not a runtime one, since it's a static import.

**Landmine — `/weekly`'s auth gate still runs before the route even resolves; "hard removal" does not mean every request to `/weekly` sees a 404.** Confirmed live this session against `proxy.ts`'s matcher (`config.matcher`, line 90): `/weekly` matches no exclusion pattern, so `proxy()` still invokes `auth(request, event)` for it exactly as it does today. Next's own middleware/proxy execution order runs this gate *before* the framework ever checks whether a page exists at the requested path (same ordering fact `proxy.ts`'s own comment block already documents for the demo-host rewrite, lines 44-48). Concretely: an **unauthenticated** request to `/weekly` is redirected to `/signin` by the existing gate — unchanged, and not a new behavior this slice introduces (`tests/unit/proxy-matcher.test.ts`'s existing `"/some/future/route"` case already proves any nonexistent gated path behaves this way today). Only a **signed-in** request to `/weekly` reaches Next's router with nothing to resolve, and gets the genuine 404 (§4.1 splits these as separate ACs, `AC-W17`/`AC-W18`, for exactly this reason). `/demo/weekly` is different: it matches the matcher's `demo(?:$|/)` exclusion, so `proxy()` never runs for it at all regardless of host or session — it 404s unconditionally the instant the file is gone (`AC-W20`).

## 2. Problem statement

The page at `/weekly` (`app/weekly/page.tsx`) is the correct feature under a name Albert now wants changed: "Weekly" only names the page's time resolution, not what it actually shows (a scorecard of five weekly-delta columns — outcomes, not just a time grain). Nothing about the page's rows, columns, computation, or drill-down needs to change; the route, the nav label, the page's own function name, its public-demo mirror, and the specific comments/tests/docs that encode the old name all do. Unlike every prior rename in this repo, the legacy path is not being kept alive as a redirect — `/weekly` and `/demo/weekly` are being retired outright, which is itself a new behavior this slice must specify and verify (§4.1, §5 `NFR-150`), not just a byproduct of the `git mv`.

## 3. Objective

A signed-in user visiting the page previously reachable at `/weekly` now reaches it at `/results`, and the header's resolution-adjacent link reads "Results." A visitor to the public demo sees the same rename at `/demo/results` and in the demo's About-page copy. A signed-in request to the retired `/weekly` path gets a genuine 404 — not a redirect, not a stub page; an unauthenticated request to it still redirects to `/signin`, exactly as it does for any other nonexistent gated path today. A request to `/demo/weekly` 404s unconditionally, authenticated or not. Every row, column, delta, state, and drill-down link renders exactly as it does today. Success = a single testable condition: a signed-in user's browser, on `NavHeader`, shows a link reading exactly "Results" whose `href` is exactly `/results`; a signed-in request to `/weekly` returns 404.
