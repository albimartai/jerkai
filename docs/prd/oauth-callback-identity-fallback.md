## 0. Scope & Sequencing Note (read first)

Both callback routes (read in full this session — `app/api/withings/callback/route.ts`, 134 lines; `app/api/whoop/callback/route.ts`, 84 lines) run identically-shaped logic: read the `{source}_oauth_state`/`{source}_oauth_user` cookies, call `auth()`, and — if it returns null — refuse immediately with `"no active session — sign in, then restart from /api/{source}/connect"`, **before ever checking whether the state/user cookies themselves are even present.** Only after that early return do they validate `code`/`state` against `{source}_oauth_state`, then compare `{source}_oauth_user` against the (now-confirmed-live) session's own `user.id` via `isBoundToInitiatingUser`. Token attribution (`saveTokens(Number(session.user.id), tokens)`) sources the id from the live session, even though the `{source}_oauth_user` cookie set at connect time (`connect/route.ts:36` in both routes) already carries the identical value.

Two real users hit exactly this early-return branch this session, both under the same circumstance: sign-in completed inside Gmail's Android in-app browser, not system Chrome. The connect click (`/api/{source}/connect`, itself gated by a live session) succeeded in that same context — meaning the browser context held a valid session at that point — but by the time the OAuth provider's redirect reached `/api/{source}/callback`, `auth()` returned null. Whether the `{source}_oauth_state`/`{source}_oauth_user` cookies set in that same connect-time response also failed to survive is genuinely unknown — the current code's ordering (session check before state check) means `"no active session"` is exactly what a reader would see whether those cookies also went missing or not; the check can never distinguish the two.

**Decision — the callback falls back to the `{source}_oauth_user` cookie's identity only when no live session exists, never as an alternative to a session that actively disagrees (confirmed with Albert, this session, 2026-09-01 — [[JerkAI - Decision Log|DL-2026-09-01-a1]]).** Considered: (A) relax the session requirement entirely, always trusting whichever of session or cookie is available and preferring the cookie if both exist; (B) fall back to the cookie only when session is strictly absent, and keep the existing mismatch-refusal exactly as today whenever a session *is* present. **Rejected A** — a live session that actively disagrees with the connect-time cookie is exactly the mid-flow-user-switch scenario AC-WS5/AC-WT4 exist to catch (user A initiates, user B is signed in by the time the provider redirects back); preferring the cookie in that case would silently attribute tokens to whoever clicked "Connect," even after the browser is now signed in as someone else — a real regression to an existing, deliberately-designed protection. **Build B.** The fallback only ever activates in the one case today's code cannot reach at all: session genuinely absent.

**Decision — the CSRF state check is not relaxed and is now the SOLE gate for a fully-lost cookie jar, which is deliberately kept, not designed around.** If a user's browser-context split loses the entire connect-time cookie pair (not just the session cookie), `{source}_oauth_state` will also be absent, and the existing `"missing or mismatched OAuth state"` check — unconditional today, unconditional after this slice — refuses the request before the new fallback logic is ever reached. This is a deliberate, useful side effect rather than an accident: once the session-absent path stops masking everything behind `"no active session"`, a genuinely total cookie loss will surface as a *different*, already-existing error message than a partial one that only lost the session cookie — giving Albert, for the first time, a way to tell the two failure shapes apart from what a future affected user reports seeing, without adding any new diagnostic code.

**Decision — one slice, both integrations, mirroring the direct precedent of "Data Page Redesign & Connect" (`lib/whoop-oauth.ts`/`lib/withings-oauth.ts`, each gaining one additive export in that same PR).** Withings' and Whoop's callback routes are structurally identical for exactly the logic this slice changes; shipping the fix for only one would leave the other's real users exposed to the identical failure the moment they try it, for no scoping benefit — this is one behavior change with two call sites, not two features.

**Decision — a second, live same-day file collision also exists and must be resolved the same way.** `[[JerkAI - Build PRD - Withings Backfill Trigger Logging]]` (also created 2026-09-01, also un-falsified) independently restructures `app/api/withings/callback/route.ts`'s `triggerBackfill()` call site and the `isFirstConnect` branch that calls it (lines 60–81, 128–130) to add logging, and explicitly assumes this slice's AC-WS21–26 allocation and build order. Build order: this slice (OAuth Callback Identity Fallback) merges first, exactly as already decided for the Whoop Historical Backfill collision. Withings Backfill Trigger Logging's build session must not assume the identity attributed to `saveTokens` is `session.user.id` — after this slice merges, the resolved identity may originate from the `withings_oauth_user` cookie fallback instead, and its log line must capture whatever identity value the merged code actually resolves and uses, not re-derive or hardcode `session.user.id`.

What this slice is NOT: no change to why the session was lost (Gmail/Android in-app-browser behavior, outside this app's control, §8 OQ-3); no change to `/api/{source}/connect`'s own session gate; no change to the CSRF state check itself; no change to `isBoundToInitiatingUser`'s existing signature or test coverage; no dashboard/UI change; no schema migration.

## 2. Problem statement

`app/api/withings/callback/route.ts` and `app/api/whoop/callback/route.ts` require a live Auth.js session on the exact request the OAuth provider redirects back to, even though the connect-time `{source}_oauth_user` cookie already carries everything needed to attribute the tokens correctly. When a browser-context split between the sign-in step and the OAuth round trip causes that specific request to arrive without the session cookie, the callback refuses outright — confirmed this session against two real onboarding attempts, both on Android, both after signing in via a magic link opened in Gmail's in-app browser.

## 3. Objective

A user who initiated `/api/{source}/connect` while genuinely signed in can complete the connection even if the final callback request arrives without a live session, provided the connect-time binding cookie is still present and the state cookie still matches — without weakening the existing protection against a session that has switched to a different user mid-flow. Success = the two real failures reproduced this session (session absent, binding cookie present) now complete successfully; a genuinely lost cookie jar (both cookies absent) still refuses, now via the pre-existing state-mismatch message rather than the session message.

### 4.1 Withings — session-absent fallback

* **AC-WS21 (bare case)** — Given a user completed `/api/withings/connect` (both `withings_oauth_state` and `withings_oauth_user` set) and, by the time Withings redirects to `/api/withings/callback`, no live session is present on that request but `withings_oauth_user` is present and the state cookie matches, When the callback runs, Then it succeeds — exchanging the code and attributing the resulting tokens to the user id carried by `withings_oauth_user`, landing exactly the row `saveTokens` would have written had a live session matched it.
* **AC-WS22 (regression — mismatched live session still refused)** — Given a live session IS present at callback time but its user id does not match `withings_oauth_user` (a genuine mid-flow user switch), When the callback runs, Then it is still refused with the existing `"the signed-in session changed..."` message, unchanged — a present session is never overridden by the cookie, only an absent one is supplemented by it.
* **AC-WS23 (state check fails closed regardless of user-cookie presence)** — Given no live session is present and `withings_oauth_state` is absent or does not match (regardless of whether `withings_oauth_user` is present, absent, or malformed), When the callback runs, Then it is refused via the existing `"missing or mismatched OAuth state"` check — never reaching identity resolution, never a 500. This covers both total cookie loss (both cookies absent) and the asymmetric case where only the state cookie was lost.
* **AC-WS24 (partial cookie loss or malformed identity, no crash)** — Given no live session is present, `withings_oauth_state` is present and matches, but `withings_oauth_user` is absent, empty, or not a value that parses to a usable positive integer, When the callback runs, Then it is refused with a clear, distinct 403 — never a 500, never an attempt to attribute tokens with no resolvable identity. The resolver validates the cookie value's shape — non-empty, `Number.isInteger(Number(value))`, and `Number(value) > 0` — before treating it as a usable fallback identity; a zero or negative value is exactly as unusable as a non-numeric one and is refused the same way, never passed to `saveTokens`.
* **AC-WS25 (no regression to the ordinary happy path)** — Given a live session IS present and matches `withings_oauth_user` (today's normal case), When the callback runs, Then behavior is byte-for-byte unchanged from today.
* **AC-WS26 (present session with unresolvable id is a mismatch, not an absence)** — Given a live session object IS present (`auth()` does not return null) but `session.user.id` resolves to the empty string, and `withings_oauth_user` is present with a valid value, When the callback runs, Then it is refused with the same mismatch message as AC-WS22 ("the signed-in session changed...") — never treated as a session-absent case, never falling back to the cookie.

## 5. Non-Functional Requirements (FDE)

All prior NFRs remain in force; the following are additive, continuing jerkai's numeric series from **NFR-135** (current live, shipped high-water mark, confirmed against `docs/codebase.md` and a fresh repo-only grep — NFR-136–140 exist only in the sibling, unbuilt "Whoop Historical Backfill on First Connect" draft and are not live), numbered NFR-136 through NFR-140. **Same unresolved cross-PRD numbering collision as §4's AC-WT range — see §6.**

* **NFR-136 — Identity resolution prefers a live, matching session; falls back to the connect-time binding cookie only when `auth()` itself returns null — never when a session object is present but its `user.id` is unresolvable.** The new resolver function's caller must key its branching on whether the session object exists (`session === null`), not on whether the extracted `sessionUserId` string is truthy — a present session whose `user.id` resolves to `""` (reachable via `lib/auth-callbacks.ts`'s `token.sub ?? ""`, NFR-138) is a present-but-mismatched case (backs new AC-WS26/AC-WT19), never a trigger for the cookie fallback. A present-but-mismatched session is never overridden by the cookie (backs AC-WS22/AC-WT15) — the fallback activates in exactly one condition: `auth()` returns null.
* **NFR-137 — The CSRF state-cookie check remains an unconditional, hard gate regardless of session presence, unmodified by this slice.** Both routes validate `code`/`state` against `{source}_oauth_state` before any identity resolution runs, exactly as today (backs AC-WS23/AC-WT16). This requires removing today's unconditional early return on `!session` (currently ahead of the state check in both files) so the state check runs unconditionally on every request regardless of session presence — the state-check-vs-identity-resolution order is unchanged, but the session-check-vs-state-check order is not.
* **NFR-138 — The fallback identity source carries no new trust boundary.** `{source}_oauth_user` is httpOnly, `Secure`, and could only ever have been set by a request that already passed `/api/{source}/connect`'s own live-session gate — the same server-issued, client-untamperable artifact the existing binding check already trusts when a session is present (§1). In practice `session.user.id` is derived from the JWT's `sub` claim via `token.sub ?? ""` (`lib/auth-callbacks.ts`) — normally always populated by `@auth/core`'s own jwt callback for this app's email provider, but not type-guaranteed to be. If it were ever empty, the cookie would carry `""`, which AC-WS24/AC-WT17's "absent or empty" handling already treats as no usable identity and refuses — so this NFR's guarantee rests on that fail-closed empty-string handling, not on an unconditional non-empty invariant at the cookie's source, and `Number()` parsing carries the same reliability the existing `Number(session.user.id)` call already has today — this is not a new failure surface this slice introduces. The foreign-key constraint on `{source}_tokens.user_id` (§1) exists as a structural backstop against a value this path should never actually produce; this slice's own tests do not exercise that backstop directly (it would require a live database write with a fabricated, malformed cookie value, which is a runtime property no static read can confirm the exact driver-level failure shape of) — if a future session ever needs to rely on it, confirm the live behavior rather than assuming it from this NFR's own text.
* **NFR-139 — A request with neither a live session nor a usable fallback identity never reaches `exchangeCode`/`saveTokens`.** It is refused before any token exchange or write (backs AC-WS24/AC-WT17). "Usable" means specifically a positive integer — `Number.isInteger` alone is not sufficient, since it admits zero and negative values that can never correspond to a real `users.id` row and would otherwise reach `saveTokens` only to fail at the foreign-key constraint as an unhandled exception rather than the mandated 403.
* **NFR-140 — `isBoundToInitiatingUser`'s existing exported signature, behavior, and test coverage are unmodified.** The new identity-resolution function is additive to `lib/{source}-oauth-binding.ts`, calling `isBoundToInitiatingUser` internally rather than duplicating its timing-safe comparison logic — no new crypto primitive is introduced (backs AC-WS25/AC-WT18).

**Verification for anything CI cannot reach (DoR gate, DL-2026-07-23-a):** the route handlers' own end-to-end wiring (cookies, redirects, `auth()`) stays manual-verification-only, as every prior OAuth-callback slice in this repo has established (§1) — `next/experimental/testing/server` cannot exercise a Route Handler or `cookies()`. The one behavior this slice adds that automated tests cannot reach at all — a real request that arrives at the callback with a valid `{source}_oauth_state`/`{source}_oauth_user` pair but no live session — is verified manually as follows, using real (not mocked) infrastructure: sign in normally, click "Connect" for either source, and once redirected to the provider's own consent screen (before completing it), use the browser's dev tools to delete only the Auth.js session cookie for `jerkai.app` — named `__Secure-authjs.session-token` in production (confirmed this session, `node_modules/@auth/core/lib/utils/cookie.js:49`, `cookiePrefix` + `authjs.session-token`), distinguishable by name alone from `{source}_oauth_state`/`{source}_oauth_user`, which are left untouched. Complete the provider's consent flow and confirm the callback succeeds (AC-WS21/AC-WT14). Separately, repeat the same sequence but delete every `jerkai.app` cookie instead of only the session cookie, and confirm the callback now returns `"missing or mismatched OAuth state"`, not a 500 (AC-WS23/AC-WT16). Add a third manual check: sign in normally, complete `/api/{source}/connect` → provider consent → `/api/{source}/callback` without touching any cookie, and confirm the redirect and the resulting `{source}_tokens` row are identical to pre-slice behavior (AC-WS25/AC-WT18). The total-cookie-loss check (AC-WS23/AC-WT16) does not itself require completing the provider's consent screen — deleting all `jerkai.app` cookies and hitting `/api/{source}/callback` directly with a placeholder `?code=&state=` is sufficient, since the state check fails before `exchangeCode` is ever reached; only the success check (AC-WS21/AC-WT14) needs a real provider round-trip.
