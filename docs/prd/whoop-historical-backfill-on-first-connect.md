## 0. Scope & Sequencing Note (read first)

Whoop's OAuth callback (`app/api/whoop/callback/route.ts`, 91 lines post-PR #39/`a29e71a` — *OAuth Callback Identity Fallback*, re-verified in the 2026-09-03 `jerkai-falsify-prd` reconciliation, not the 84-line pre-merge version this section originally cited) has never had a backfill mechanism — it resolves the connecting user's identity via `resolveCallbackIdentity()` (`lib/whoop-oauth-binding.ts`), exchanges the code, saves tokens, and redirects to `/status`, with no equivalent of Withings' `triggerBackfill()`. This isn't an oversight discovered today: `lib/readings.ts:6` already names it in a comment as "the future Whoop historical backfill," written before Withings' own backfill shipped. The consequence surfaced concretely this session: querying production (`biometric_readings`, `sync_runs`, `whoop_workouts`, read-only role, 2026-09-01) for a real user who connected Whoop on 2026-08-31 shows exactly one cron run recorded (today, 80 rows) and a `biometric_readings` date range of 2026-08-25–2026-09-01 — eight days, matching `app/api/whoop/sync/route.ts`'s `DEFAULT_WINDOW_DAYS = 7` plus one day of accumulation, not a backfill. Albert's own account has deeper history (back to 2026-08-09 and earlier), but that predates this connect flow entirely — `[[JerkAI - Decision Log]]` `DL-2026-07-15` records it as a one-off "Whoop-direct historical backfill," run manually via a standalone script before the multi-tenant `/api/whoop/connect` flow existed. No other connected user has ever received anything equivalent.

**Decision — the backfill window is 90 days, not Withings' 365 (confirmed directly by Albert, 2026-09-01 — logged as [[JerkAI - Decision Log]] `DL-2026-09-01-c`).** Considered: (A) mirror Withings exactly at 365 days; (B) 90 days. **Rejected A** — JerkAI's own read surface never displays more than 90 days of history regardless of how far back the underlying rows go: `app/weekly/page.tsx:14` declares `WEEKLY_LEDGER_WINDOW_DAYS = 90` and `app/daily/page.tsx:16` declares `MAX_WINDOW_DAYS = 90` as the two pages' own hard caps (both read live this session). A 365-day backfill would write 275 days of rows no page in this app can ever read, at real cost against Whoop's rate limits for zero product benefit. **Build B.** This also has a structural benefit Withings' 365-day window didn't: `app/api/whoop/sync/route.ts`'s own header comment (line 42, read live this session) already documents "chunked date ranges (~90 days each, to stay inside function-duration and Whoop rate limits)" as the established safe unit for a Whoop historical pull — so a single 90-day backfill call needs no additional internal chunking logic the way Withings' 365-day backfill did (its own NFR-101 fallback to sequential ~90-day windows). One call, one window, done.

**Decision — the mechanism mirrors `lib/withings-oauth.ts`'s `triggerBackfill()`/`backfillTargetOrigin()`/`BACKFILL_WINDOW_DAYS` function-for-function, not a new design.** These functions were originally inline in `app/api/withings/callback/route.ts` (134 lines, as first read this session 2026-09-01) but were relocated into `lib/withings-oauth.ts` by [[JerkAI - Build PRD - Withings Backfill Trigger Logging]] (PR #41/`6f47c9f`, correction PR #42/`3e1acc7`, both merged to `main` 2026-09-03) — the route file is now 111 lines and calls them as a thin caller (corrected in the 2026-09-03 round-2 `jerkai-falsify-prd` reconciliation). They already solve the exact problem this slice has — detect a true first connect atomically, schedule a wide-window sync call after the redirect without blocking it or risking the callback's own function-duration budget, target the deployment that's actually handling the request rather than the pinned production domain. Building a second, independently-designed mechanism for Whoop would be needless divergence; this slice ports the same shape under Whoop's own names, adding the mirrored helpers to `lib/whoop-oauth.ts` (alongside `saveTokens`/`isFirstConnect`), matching the current repo convention rather than the pre-PR#41/#42 inline-in-route-file shape.

What this slice is NOT: no retroactive backfill for a user who already has a `whoop_tokens` row before this slice ships (§8 OQ-2); no change to `lib/whoop-api.ts`'s rate-limiting (already sufficient, §1); no change to any Withings file; no dashboard UI change; no disconnect/revoke feature; no schema migration.

## 2. Problem statement

`app/api/whoop/callback/route.ts` has no historical backfill: a newly connected user's Whoop data starts accumulating only from the moment they connect, one day at a time, via the daily cron's 7-day trailing window (`app/api/whoop/sync/route.ts#DEFAULT_WINDOW_DAYS`). A user who has worn a Whoop band for months arrives in JerkAI with, at best, a week of visible history — confirmed this session against a real connected production user (`user_id 2`: 78 `biometric_readings` rows and 2 `whoop_workouts` rows, both spanning only 2026-08-25–2026-09-01). Withings' equivalent integration solved this on first connect (`app/api/withings/callback/route.ts`); Whoop's callback never got the equivalent treatment.

## 3. Objective

A user's first-ever Whoop connect automatically backfills their trailing 90 days of history — recovery, sleep, cycle, and workout data — without blocking the connect flow's redirect or exceeding Whoop's rate limits, and without ever re-running for a routine reconnect. Success = a user who connects Whoop for the first time today has up to 90 days of pre-existing `biometric_readings`/`whoop_workouts` rows within moments of connecting, rather than needing to wait 90 days of daily cron runs to accumulate the same coverage.

Written as testable Given/When/Then. Continues the existing **AC-WT** series (Whoop, `[[JerkAI - Build PRD - Whoop Multi-Tenancy]]`), numbered from **20** — current live high-water mark is **AC-WT19**, not AC-WT13 as originally drafted (AC-WT14–19 were shipped by [[JerkAI - Build PRD - OAuth Callback Identity Fallback]], PR #39/`a29e71a`, confirmed against `docs/codebase.md`'s AC-WT row and a fresh repo grep — corrected in the 2026-09-03 `jerkai-falsify-prd` reconciliation).

### 4.1 First-connect backfill

* **AC-WT20 (bare case)** — Given a user completes the Whoop OAuth connect flow for the **first time** (no pre-existing `whoop_tokens` row before this connect), When the callback completes, Then a backfill covering the trailing 90 days is triggered automatically (§0), and resulting rows land in `biometric_readings` (recovery/sleep/cycle-mapped metrics, `source = 'whoop'`) and `whoop_workouts` for that window wherever Whoop has data — using the exact same mapping (`lib/whoop-map.ts`) and write path (`lib/readings.ts#upsertReading`) the daily cron already uses, not a separate code path.
* **AC-WT21 (reconnect does not re-backfill)** — Given a user who already has a `whoop_tokens` row (reconnecting), When the callback completes, Then no backfill is triggered — only the normal token update happens, mirroring `whoop_tokens`' existing `on conflict (user_id) do update` behavior, so a routine reconnect never re-consumes 90 days of Whoop rate-limit budget or re-fires a redundant sync.
