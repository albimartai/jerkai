## 0. Scope & Sequencing Note (read first)

### 0.1 Why this slice, why now

Log Meal (`/log-meal`) and Settings → Targets (`/settings/targets`) are today two separate gated pages that both exist to answer one question — "am I on track today, and what should I be aiming for?" — split across a page you log to and a page you configure from, reachable only via two separate nav links (`app/ui/nav-header.tsx:77-96`). Albert wants them presented as one page, "Fuel," matching a design draft he produced (`Fuel.dc.html`, this session's Source artifact) that puts a "View" segmented control at the top switching between a Log Meal view and a Targets view, adds a persistent running-total readout to the Log Meal view, and adds a target-history table to the Targets view.

**Decision — `/log-meal` and `/settings/targets` are hard-removed, not redirected (Albert's explicit direction, 2026-09-14; DL-2026-09-14-a1).** Considered: (A) a single-hop `redirect("/fuel")` stub at each old path, the convention used by the earliest page renames (`/status`→`/data`, still a stub per `app/status/page.tsx`); (B) hard removal — no stub file at all, matching the convention this repo has used for every rename since `/weekly`→`/results` (`docs/prd/rename-weekly-page-to-results.md`, `docs/prd/rename-results-page-to-body.md`). Albert confirmed (B) explicitly ("I don't want redirects from old routes; I want direct routes eg /fuel"), extending the same precedent from a rename to a merge. Build (B): a signed-in request to either old path reaches Next's router with nothing to resolve and gets a genuine 404 (proxy.ts's session gate still runs first for `/settings/targets` and `/log-meal` — neither matches any matcher exclusion, confirmed live this session against `proxy.ts`'s `config.matcher`, so an unauthenticated request still redirects to `/signin`, unchanged).

**Decision — Fuel is a new top-level nav item, not a header CTA or a Settings-only link (Albert's explicit choice among presented options; DL-2026-09-14-a2).** Considered: (A) a new permanent nav tab (Body / Daily / Fuel / Connect); (B) replacing the "+ Log meal" header CTA's slot with a "Fuel" CTA, no permanent tab; (C) reachable only from a Settings surface. Albert chose (A). Build (A): `app/ui/nav-header.tsx`'s live-variant link list drops its separate "Targets" and "Log Meal" `<Link>` elements (lines 77-96) and gains one "Fuel" `<Link href="/fuel">`.

**Decision — target editing on Fuel stays an always-visible, pre-filled edit form (Albert's explicit choice among presented options; DL-2026-09-14-a3).** Considered: (A) keep today's always-visible form as-is; (B) a read-only current-target summary with an "Edit" disclosure that reveals the form. Albert chose (A) — no change to `app/ui/targets-form.tsx`'s form-always-rendered behavior.

**Decision — the design draft's "Set quarterly" tag is dropped (Albert's explicit choice among presented options).** The mockup shows a `tag-outline` badge reading "Set quarterly" next to the Targets view's "Macro targets" heading. Confirmed live this session: nothing in `lib/targets.ts`, `lib/target-validation.ts`, or `app/settings/targets/actions.ts` tracks, computes, or enforces any update cadence — `daily_targets` is a plain insert-only effective-dated table with no cadence column or check. Rendering the tag verbatim would assert a product behavior that does not exist. Build without it — no cadence copy, tag, or logic is added.

### 0.2 What the nav-highlight and CTA-text ACs this slice retires actually asserted, and why they no longer apply

`tests/unit/nav-header-variants.test.tsx`'s `AC-D19`/`AC-D20` block (lines 63-78, `DO NOT EDIT` header, PRD target: Nav Header Cleanup & Status Page Chrome) asserts the live variant's "Log Meal" link reads exactly "Log Meal" with no border classes. Once Log Meal is no longer its own nav link — it is a view inside Fuel, reached via `/fuel` — there is no element left for this assertion to describe; the whole `describe` block is retired, not value-edited (§1). The same file's `AC-DS18`–`AC-DS21` block (lines 90-159, PRD target: Data Page Redesign & Connect) asserts active-highlight behavior for four `active` values including `"logmeal"` and `"targets"`; those two values (and their `/log-meal`/`/settings/targets` href lookups) are retired the same way, replaced by one new `active="fuel"` case. `AC-DS18` (`active="connect"`) and `AC-DS20` (`active="body"`/`"daily"` regression) remain in force — Connect, Body, and Daily are unaffected by this slice — amended only to swap `/log-meal`/`/settings/targets` for `/fuel` in their "no other link is active" assertion lists (§1).

### 0.3 Landmine — the day's entries fetch is duplicated once, deliberately, rather than restructuring `MealEntriesList`

The Total · Today card needs the same day's meal entries `MealEntriesList` already fetches via `listMealEntriesForDate` (`app/log-meal/actions.ts:190-194`, confirmed live this session). Lifting that fetch out of `MealEntriesList` into a shared parent would touch a component with two dedicated component-tier test files (`tests/component/log-meal-panel.test.tsx`, `tests/component/meal-entries-list.test.tsx`) that construct it as a standalone, self-fetching unit. This slice instead gives the new `FuelTotalCard` its own call to the same already-exported, already-safe-to-call-more-than-once `listMealEntriesForDate` function, driven by the same `entryDate`/`refreshToken` props `LogMealPanel` already threads to `MealEntriesList` (`app/ui/log-meal-panel.tsx:44-49`). This is one extra read per render of the panel, not a new query shape or a new table scan (`fetchMealEntriesForDate` is a `select` filtered by `entry_date` (indexed, per `migrations/1784567579158_create-manual-macro-entries-and-daily-targets.js:37`) and `user_id` (no index exists on this column) — still a small per-user row count, not a full table scan, so the accepted-risk conclusion is unchanged) — accepted as the lower-risk choice over restructuring two already-tested components. Do not "fix" this by threading entries down from `MealEntriesList` instead — that inverts an intentional choice.

What this slice is NOT: a schema change; a change to macro validation rules; a change to the `/daily` dashboard's own calorie strip or target resolution; a URL-addressable view-toggle state; a public-demo mirror of Fuel; any Favorites/Recents or LLM-estimation feature.

## 2. Problem statement

Today, "how am I doing against my targets, and what should today's target be" requires two separate authenticated pages reached by two separate nav links (`/log-meal`, `app/log-meal/page.tsx`; `/settings/targets`, `app/settings/targets/page.tsx`) that share no UI and cross-link only once, awkwardly, from inside a post-save success message ("No target set yet — set targets", `app/ui/log-meal-form.tsx:238`). Neither page shows the other's information: Log Meal never surfaces target history, and Targets never surfaces today's logged total. Albert's design draft consolidates both into one page, "Fuel," with a view toggle and two new readouts (a persistent running total, a target history table) that read data the app already computes but has never surfaced together.

## 3. Objective

A signed-in user visits `/fuel` and can, without navigating away, log a meal and see today's running total against their current target, or switch to see and edit their target history — the same two capabilities `/log-meal` and `/settings/targets` provided separately, now in one place, with two new readouts neither page had. Success = a user who has just saved a meal on the Log Meal view, then clicks "Targets," sees their just-effective target and its full history without a page reload, and clicking back to "Log meal" shows the same day's entries and total unchanged.
