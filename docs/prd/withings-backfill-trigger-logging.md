## 0. Scope & Sequencing Note (read first)

`app/api/withings/callback/route.ts` (read in full this session, 141 lines — reflects the merged state after [[JerkAI - Build PRD - OAuth Callback Identity Fallback]], PR #39, `a29e71a`) already ships the behavior this PRD's predecessor, [[JerkAI - Build PRD - Withings Smart-Scale Integration]], specified: on a true first connect (`isFirstConnect(existingRowFound)` true, line 135) it calls `triggerBackfill()` (line 136), which schedules a 1-year historical sync via `next/server`'s `after()`; on a reconnect it does nothing further and just redirects. That mechanism is correct and shipped (PR #33, `docs/codebase.md` confirms AC-WS1–20 all held their stated meaning through four falsify rounds and one merge-gate pass). What it does not do is say anything about what happened: today, a genuine first connect whose trigger fires and completes successfully, a first connect whose trigger silently fails, and an ordinary reconnect that correctly never fires anything all produce **zero log output** in the common case (`triggerBackfill()`'s only existing log lines are `console.error` calls for a missing `CRON_SECRET`, line 69, or a failed internal fetch, lines 81/84 — nothing logs on the success path, and nothing logs the deliberate no-op on reconnect). A real onboarding session this week hit exactly this gap: a friend's (Graydon's) first Withings connect completed, and there was no way to tell from logs alone whether the backfill had fired and quietly failed, or had never been called at all.

This slice closes that gap with pure observability — four log lines, one per state a callback can end in — and changes no firing condition, no timing, and no date-window logic. It is deliberately scoped as its own PRD rather than folded into either sibling in flight: the separately-drafted, already-reconciled [[JerkAI - Build PRD - OAuth Callback Identity Fallback]] is about session-absent identity resolution in *both* Withings' and Whoop's callback routes — an unrelated mechanism that happens to touch the same Withings file, and bolting a second, unrelated behavior change onto it would turn a one-concern slice into two (confirmed with Albert this session, not yet allocated a Decision Log id, flagged for logging in §6). The unbuilt [[JerkAI - Build PRD - Whoop Historical Backfill on First Connect]] draft is the PRD that will eventually give Whoop its own `triggerBackfill()` — Whoop has none today (confirmed by grep this session: zero matches for `backfill` in `app/api/whoop/callback/route.ts`) — so a Whoop-side version of these same four log states cannot be specified against real code yet; a Whoop-side version of this slice's four-state log-line pattern is not yet named anywhere in that draft's own text (confirmed by grep this session — no mention of "log line" or "trigger logging" in it); it is this slice's own fast-follow to propose there once that draft is next revised, not an existing cross-reference (§8 OQ-3).

**Decision — this slice is Withings-only, additive-logging-only, and lives in its own PRD (confirmed with Albert this session, not yet allocated a Decision Log id, flagged for logging in §6).** Considered: (A) fold these four ACs into OAuth Callback Identity Fallback's own §4, since both touch `app/api/withings/callback/route.ts`; (B) fold them into the unbuilt Whoop Historical Backfill draft, since that PRD already owns the `triggerBackfill()` concern going forward; (C) a new, standalone thin-slice PRD scoped to exactly this behavior. **Rejected A** — identity-fallback and backfill-observability are two unrelated mechanisms; the OAuth PRD's own §0 already states "this is one behavior change with two call sites, not two features," and adding a second, unrelated behavior change would contradict that framing and its own AC-WS21–26 numbering, which is entirely about session/cookie resolution. **Rejected B** — that draft is about giving Whoop a `triggerBackfill()` it does not yet have; Withings' logging fix is buildable and valuable today, independent of whether or when that draft ships, and tying it to an unbuilt, not-yet-falsified sibling would block a same-day fix behind an unrelated slice's own timeline. **Build C.**

What this slice is NOT: no change to whether, when, or with what date window `triggerBackfill()` fires (AC-WS8/AC-WS10/NFR-98/NFR-105/NFR-109 unchanged); no change to `app/api/withings/sync/route.ts`; no change to the CRON_SECRET-missing early return's existing message or behavior (AC-WS31); no Whoop equivalent; no new alerting/dashboard/UI; no schema migration.

## 2. Problem statement

`app/api/withings/callback/route.ts`'s `triggerBackfill()` and the `isFirstConnect` branch that calls it produce no log output on the two most common paths — a successful first-connect backfill, and a correctly-skipped reconnect — and produce log output on the two failure paths (missing `CRON_SECRET`, a failed internal fetch) that is real but untested, so a regression there would not be caught. A genuine first-connect backfill that silently failed and a first connect whose trigger was never called at all are indistinguishable after the fact, and a correctly-skipped reconnect looks identical to both. Confirmed this session against a real onboarding attempt (Graydon's first Withings connect) that left no log trail either way.

## 3. Objective

Every path `app/api/withings/callback/route.ts`'s backfill-trigger logic can take — triggered, succeeded, failed, or skipped-as-a-reconnect — writes one distinguishing, falsifiable log line, with the trigger line written before the internal fetch is attempted rather than only on an eventual outcome. Success = the four states are each independently observable in server logs, and a regression to any one of them (e.g. the success line silently stops firing, or the skip line gets removed) fails a test rather than only surfacing the next time a real user's connect goes uninvestigated.

### 4.1 Backfill-trigger logging (bare case first)

* **AC-WS27 (bare case)** — Given a user's Withings connect completes with no pre-existing `withings_tokens` row (a true first connect, `isFirstConnect(existingRowFound)` true) and `CRON_SECRET` is set, When the callback decides to fire the backfill, Then a log line is written identifying the connecting user and the computed `start`/`end` date window (the same values used to build the actual sync request URL, never recomputed independently, NFR-142) — written before the internal fetch to `/api/withings/sync` is attempted, not only once that fetch resolves or fails.
* **AC-WS28 (triggered backfill succeeds)** — Given AC-WS27's trigger log was written, When the internal fetch to `/api/withings/sync` returns a response with `res.ok` true, Then a log line confirms the backfill request completed successfully, identifying the same user as AC-WS27's trigger line.
* **AC-WS29 (triggered backfill fails — existing behavior made falsifiable)** — Given AC-WS27's trigger log was written, When the internal fetch either returns a non-2xx response or throws, Then a log line records the failure with the response status and body text (non-2xx case) or the caught error (thrown case) — the same two `console.error` calls that already exist in `app/api/withings/callback/route.ts` today (lines 81 and 84), now covered by a test that would catch a regression to either.
* **AC-WS30 (reconnect explicitly logs a skip)** — Given a user's connect completes as a reconnect (`isFirstConnect(existingRowFound)` false — a `withings_tokens` row already existed), When the callback runs, Then a log line explicitly states the backfill was not triggered because this was a reconnect, identifying the user — distinguishing this correctly-skipped case from a first connect whose trigger silently failed to fire at all (today, both produce zero log output).
* **AC-WS31 (regression — CRON_SECRET-missing case unchanged)** — Given `CRON_SECRET` is not set, When `triggerBackfill()` runs (on a true first connect), Then the existing `console.error("withings backfill not triggered: CRON_SECRET is not set")` (line 69) fires exactly as it does today, and no AC-WS27 trigger line is written for that request — a missing-configuration failure stays distinguishable from AC-WS27's "decided to fire" line, which asserts a `CRON_SECRET` is actually present.

**On user-verb phrasing (pre-empting FM-05, matching the framing every prior OAuth-callback slice in this repo has established):** every AC above describes server-side logging as a side effect of a machine-to-machine OAuth redirect chain, not a rendered UI interaction — there is no UI in this slice — verified by exercising the logging logic directly, never a component test.

## 5. Non-Functional Requirements (FDE)

All prior NFRs remain in force, including NFR-98/NFR-105/NFR-109 (the backfill-trigger mechanism this slice adds logging to, unmodified). The following are additive, continuing jerkai's numeric series from **NFR-140** (current live, shipped high-water mark) — [[JerkAI - Build PRD - OAuth Callback Identity Fallback]] **has shipped** (PR #39, `a29e71a`, merged to `main`; confirmed against `docs/codebase.md`: "high-water mark NFR-140 as of this slice (NFR-136–140, OAuth Callback Identity Fallback)", and a fresh repo grep, 2026-09-03). The unbuilt Whoop Historical Backfill on First Connect draft still independently cites NFR-136–140 for itself in its own text — now stale against the shipped OAuth PRD's claim to that same range, and that draft's own problem to re-derive when it is next reconciled, not this PRD's. This PRD allocates **NFR-141–144**, confirmed correct and current as of this check — no renumbering needed.

* **NFR-141 — Every log line this slice adds is unit-testable without driving the route handler's own `cookies()`/`auth()` wiring, mirroring `isFirstConnect`'s own extraction rationale (§1, NFR-99's precedent).** The triggering condition for each of the four states (AC-WS27–31) is a pure decision keyed only on already-available values (`isFirstConnect`'s boolean, the fetch outcome, whether `CRON_SECRET` is set) — none of it requires a live session, cookies, or a real HTTP request to exercise in a test. No existing test in this repo mocks or exercises `next/server`'s `after()` (confirmed by repo-wide grep, 2026-09-03) — the build session establishes this seam for the first time here, most simply via `vi.mock("next/server", () => ({ after: (cb: () => void) => cb() }))` so the AC-WS28/AC-WS29 fetch-outcome assertions run synchronously under test.
* **NFR-142 — The trigger log's date window is derived from the same `start`/`end` values used to build the actual `/api/withings/sync` request URL, never recomputed independently.** A second, independent computation of "365 days ago" at logging time could drift from the value actually sent (e.g. straddling a day boundary between the two computations), producing a log line that describes a window the request didn't actually use — the failure mode this NFR exists to prevent.
* **NFR-143 — No log line this slice adds ever includes a token, secret, or credential.** `triggerBackfill()`'s internal fetch sends `CRON_SECRET` only as a request header (line 79), never logged; the existing failure logs (lines 81, 84) already log only `res.status`/response body text/the caught error, not the request itself — this slice's new lines (user id, dates, success/skip confirmation) carry the same property forward, not a new one.
* **NFR-144 — For a single request, the trigger log (AC-WS27) is always written before that same request's eventual success (AC-WS28) or failure (AC-WS29) log, never the reverse and never only the latter.** This is what makes "triggered and never finished" distinguishable from "never triggered" — the property AC-WS27's own bare case exists to establish.

**Verification for anything CI cannot reach (DoR gate, DL-2026-07-23-a):** the route handler's own end-to-end wiring (cookies, redirects, `auth()`, the real `after()`-scheduled fetch actually reaching Vercel's runtime) stays manual-verification-only, as every prior OAuth-callback slice in this repo has established (§1) — `next/experimental/testing/server` cannot exercise a Route Handler or `cookies()`. Manual check: complete a real Withings first connect (dev or Preview) and confirm, in that deployment's server logs, that the AC-WS27 trigger line appears before either the AC-WS28 success line or the AC-WS29 failure line, in that order, for the same user id and window; separately, complete a reconnect and confirm only the AC-WS30 skip line appears, with neither AC-WS27 nor AC-WS28/29 present. Do this on a Preview or dev deployment, not by inferring from a production URL after merge — a live-domain check alone cannot distinguish "not deployed yet" from "logging never fires" (mirrors the DoRD's own host-routing verification discipline).
