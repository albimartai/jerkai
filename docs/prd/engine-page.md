## 0. Scope & Sequencing Note (read first)

### 0.1 Why this slice, why now

Body (body composition: body fat, weight, lean mass) and Fuel (energy balance: Log Meal + Targets) have both shipped. Engine is the third leg of the naming scheme Albert sketched this project (Body / Engine / Fuel), carrying the training driver (Day Strain) and its recovery guardrails (Recovery Score, HRV, RHR) — exactly the two columns (Strain, Recovery) the sibling `Drop Strain and Recovery Columns from the Weekly Ledger` slice deliberately removed from Body's landing page, on the explicit premise (`DL-2026-09-13-a1`'s sibling decision, `DL-2026-09-13-a3`) that, in the Decision Log's own words, "a future Engine/Performance page re-derives its own aggregation from scratch rather than un-deleting this shape." This slice is that future slice.

### 0.2 Decision — HRV ships as a plain week-over-week delta, not a rolling-baseline comparison (Albert's explicit choice this session; `DL-2026-09-15-a1`)

Considered: (A) the originally-discussed shape — a 7-day rolling HRV average compared against the user's own 30–60 day rolling baseline, on the premise that raw HRV isn't meaningful without a personal baseline; (B) the same plain shape already used for Strain and RHR — a 7-day-rolling-average endpoint at each week's end, minus the prior completed week's endpoint. Albert chose (B). (A) would require a new baseline-window config value and a decision about how much history is needed before a baseline is "valid" — neither exists anywhere in this codebase today, and neither should be invented un-confirmed. Build (B): HRV, Strain, and RHR all share one column shape this slice. A rolling-baseline HRV view remains something Albert can raise again as its own future request; it is not carried forward here as a planned item (§8 OQ-1 is a separate, narrower open question about coloring only).

### 0.3 Decision — Strain/Recovery/HRV/RHR stay duplicated on `/daily`; Engine does not become their sole home (Albert's explicit choice this session; `DL-2026-09-15-a2`)

Considered: (A) leave `/daily`'s main-stack Strain strip, its guardrail readout row, and its collapsible Whoop detail (HRV, RHR, Recovery Score) exactly as they are — Engine adds a new weekly-cadence *view* of the same underlying series, not a relocation; (B) remove these four from `/daily` now that Engine exists, making Engine their one home. Albert chose (A). Build (A): `app/ui/dashboard.tsx`, `lib/dashboard/strain.ts`, and `lib/dashboard/readouts.ts` are **not modified** by this slice (§1) — the same protected-file convention the sibling column-drop slice already established (its own `NFR-161`/`NFR-162`), now extended to Engine for the same reason: these three files serve `/daily`'s independent, unrelated-to-the-ledger read path (`DashboardData.series`, confirmed live this session), and Engine reads the same shape via its own separate `fetchDashboardData(WEEKLY_LEDGER_WINDOW_DAYS, userId)` call in `app/engine/page.tsx`. This is **not** the same fetched array — `/`, `/body`, `/daily`, and `/engine` each call `fetchDashboardData` independently, at their own request time, so a value written between two page loads can legitimately differ across them for a brief window. This is an accepted, pre-existing property of the read path, not a new guarantee Engine introduces or needs to enforce.

### 0.4 Decision — VO2max is out of scope, with no forward commitment (Albert's explicit choice this session; `DL-2026-09-15-a3`)

Considered: (A) defer VO2max as a named fast-follow, the way this repo usually files a deliberately-deferred feature; (B) drop it from scope entirely, with no reference to future work. Albert chose (B) — stronger than the repo's usual deferral convention. ### 0.7 Note — Recovery's red-zone threshold reuses `RecoveryConfig.redBelowPct` (34); its `windowDays` (7) is not used

## 2. Problem statement

The training driver (Day Strain) and its recovery guardrails (Recovery Score, HRV, RHR) exist only at a daily/7-day-rolling cadence today, on `/daily`'s main stack and its collapsible Whoop detail. There is no weekly-cadence "data product" view of these four metrics — the kind of review Albert already does for body composition on `/body` — and no page reachable from a "training" mental model, as opposed to "body comp" (Body) or "energy balance" (Fuel).

## 3. Objective

A signed-in user visiting `/engine` sees one row per ISO week (newest first), each with four columns — Strain, Recovery, HRV, RHR — computed independently of Body's ledger and without altering anything `/daily` already renders. The live nav shows Body, Engine, Fuel, Daily, Connect in that order. Success = two testable conditions: `buildEngineLedger`'s output carries exactly the four documented column shapes, and `NavHeader`'s live variant renders the five links in the stated order with `/daily`, `/body`, `/fuel`, `/connect`, and their existing tests, unchanged in behavior.

### 4.1 Engine page, bare case and gap/insufficient-data handling

* **AC-E1 (bare case)** — Given any signed-in user, When they request `/engine`, Then the page renders `NavHeader` with "Engine" highlighted and a table with exactly four data columns, in this order: Strain, Recovery, HRV, RHR — one row per ISO week, newest first (mirrors `AC-W1`/`AC-W5`'s pattern, freshly built).
* **AC-E2** — Given a week has zero raw readings across all four of Day Strain, Recovery Score, HRV, and RHR, Then that week collapses to a single "no data this week" gap row rather than four "insufficient data" cells (mirrors `AC-W7`/`AC-W33`'s pattern; independently re-derived per `DL-2026-09-13-a4`'s sibling precedent — this module does not import `ledger.ts`'s `isEmptyWeek`).
* **AC-E3** — Given a week has fewer than `DASHBOARD_CONFIG.ledger.minDaysPerWeek` (4) raw readings for one specific series that week, Then only that series' cell renders "insufficient data" (em-dash, day-count tooltip) — checked independently per column, so a week can show a computed Strain value alongside an "insufficient data" Recovery cell if only Recovery's device data was sparse that week.

### 4.2 Column shapes

* **AC-E5 (Strain)** — Given a completed week with ≥4 days of Day Strain data, Then the Strain cell shows the signed delta between this week's 7-day-rolling Day Strain average (its value at the week's last present day) and the prior completed week's own endpoint — e.g. "+1.2"/"−1.2"/"±0.0", one decimal, no unit — rendered in a single neutral tone (no good/warning color; Day Strain is a driver, not a directional guardrail — `NFR-175`, matching `AC-W4`'s "weight asserts no direction" precedent).

* **AC-E8 (Recovery)** — Given a completed week with ≥4 days of Recovery Score data, Then the Recovery cell shows "`{avgPct}% · {redDays} red {day or days}`" — the mean Recovery Score over the week's present days, and a count of that week's present days with a Recovery Score below `DASHBOARD_CONFIG.recovery.redBelowPct` (34) — freshly computed by `lib/dashboard/engine.ts`, not `ledger.ts`'s deleted `recoveryCell` (`DL-2026-09-13-a3`).
