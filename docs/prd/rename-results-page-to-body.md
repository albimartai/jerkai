Relabel current "Results" page (`/results`) to "Body" ( /body ).

**Decision — `/results` and `/demo/results` are hard-removed, not redirected (Albert's explicit direction, 2026-09-13; DL-2026-09-13-a1).** Considered: (A) a single-hop `redirect("/body")` stub, the convention every rename *before* the Weekly→Results slice used; (B) hard removal, repeating the Weekly→Results convention — no stub file at all, so a request to `/results` gets Next's ordinary 404 for a route that does not exist. **Decision — the public demo surface is in scope (Albert's explicit direction; DL-2026-09-13-a2).** Considered: (A) live app only, leaving `/demo/results` and the demo About page's "Results" list item unrenamed until a separate fast-follow; (B) rename both surfaces in the same slice. Build (B): `app/demo/results/` relocates to `app/demo/body/`, `proxy.ts`'s `DEMO_HOST` rewrite target changes, and the About page's copy changes.

### 0.2 What "hard removal" actually requires, mechanically

Identical mechanism to the Weekly→Results rename, restated for self-containment: because `/results` is not becoming a redirect stub, there is no new `app/results/page.tsx` to write after the move — `git mv app/results app/body` (and `git mv app/demo/results app/demo/body`) leaves nothing behind at the old paths. `app/page.tsx`'s import of `WEEKLY_LEDGER_WINDOW_DAYS` must follow the file to its new path (`app/page.tsx:7`), a compile-time failure if missed, not a runtime one.

**Landmine, restated from the predecessor PRD — `/results`'s auth gate still runs before the route even resolves.** Confirmed live this session against `proxy.ts`'s matcher (`config.matcher`, line 90): `/results` matches no exclusion pattern, so `proxy()` still invokes `auth(request, event)` for it. An **unauthenticated** request to `/results` is redirected to `/signin` by the existing gate — unchanged, not a new behavior (`tests/unit/proxy-matcher.test.ts`'s existing `"/some/future/route"` case already covers any nonexistent gated path taking this branch, though note that case mocks `auth()` rather than proving the redirect end-to-end — same caveat the predecessor PRD's own reconcile line already flagged, FM-03-adjacent; treat as suggestive, not proof). Only a **signed-in** request to `/results` reaches Next's router with nothing to resolve, and gets the genuine 404. `/demo/results` is different: it matches the matcher's `demo(?:$|/)` exclusion, so `proxy()` never runs for it at all — it 404s unconditionally the instant the file is gone.
