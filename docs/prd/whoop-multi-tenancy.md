## 0. Scope & Sequencing Note (read first)

Whoop is still architecturally single-user after both prior slices — verified this session directly against the current repo state. `whoop_tokens` holds exactly one row (`id smallint primary key default 1 check (id = 1)`, `migrations/1784135751252_create-whoop-tokens-and-workouts.js`); `lib/whoop-oauth.ts`'s `saveTokens`/`loadTokens` hardcode `where id = 1`; `app/api/whoop/connect/route.ts` and `app/api/whoop/callback/route.ts` gate on session *presence* only, never read `session.user.id`; `app/api/whoop/sync/route.ts` resolves one `primaryUserId` via `resolvePrimaryUserId()` (`lib/primary-user.ts`, added by the Multi-User Data Model Retrofit) and attributes every pulled reading to it in a single pass; `whoop_workouts` carries no user column at all; `sync_runs` carries no user column either, and `app/status/page.tsx` reads it as one global, unscoped view. **The Multi-User Data Model Retrofit's own §0 explicitly deferred both `whoop_tokens` and `whoop_workouts` to this slice** ("both explicitly deferred to 'Whoop Multi-Tenancy'") — this is not new scope, it is scope that PRD already named and handed off.

**Decision — the OAuth connect flow identifies the user from the session, not from a new identity parameter threaded through Whoop (FDE call, extending the existing CSRF design).** `/api/whoop/connect` already sets an httpOnly `whoop_oauth_state` cookie and `/api/whoop/callback` already re-checks `auth()` as defense in depth. Considered encoding the initiating user's id into the Whoop `state` parameter itself. Rejected: `state` round-trips through Whoop's own redirect and consent screen — treating it as a pure CSRF nonce (its documented purpose) rather than overloading it with identity keeps Whoop's OAuth contract unchanged and avoids a second decode/validate step for a value Whoop itself never needs to see. **Decision — bind the initiating user across the roundtrip with a second httpOnly cookie, not merely a fresh `auth()` call at callback time.** Reading `session.user.id` fresh at callback time is *almost* sufficient (the existing state-cookie CSRF protection already ties the callback to the same browser that started the flow) but leaves one narrow gap: if the browser's active session changed between initiating and completing the flow (log out, a different user logs in, Whoop's redirect completes), the token would silently attribute to whoever is signed in *now*, not whoever clicked "Connect." A second cookie, `whoop_oauth_user`, set to `session.user.id` alongside `whoop_oauth_state` at connect time and compared against the callback's own fresh `session.user.id`, closes this the same way the state cookie already closes the CSRF gap — mismatch is refused with the same "restart from /api/whoop/connect" shape (AC-WT4, NFR-78).

**Decision — the pre-existing singleton rows backfill to `PRIMARY_USER_EMAIL`'s resolved user, not to "the sole row in `users`."** The Multi-User Data Model Retrofit's own migration used "exactly one row in `users`" as its backfill precondition, which was safe *then* because no second person could yet be invited. That assumption is no longer safe here: this slice ships after data isolation, so a second (or third) person may already be an allowlisted, signed-in user by the time this migration runs, while the *Whoop connection itself* was still only ever made on Albert's behalf. Copying the prior migration's precondition verbatim would misattribute Whoop's history the moment more than one user exists. This migration instead resolves the same `PRIMARY_USER_EMAIL` the ingest and (until this slice) Whoop-sync routes already use for exactly this purpose (AC-WT10/AC-WT11/AC-WT13, NFR-81). **The `PRIMARY_USER_EMAIL` resolution — and its fail-closed abort — is triggered only when a row actually exists to backfill.** `whoop_tokens`/`sync_runs` hold zero rows on every fresh disposable CI branch (`scripts/ci/neon-branch.mjs` creates a genuinely empty database) and, in production, before Albert's own first Whoop connection — an unconditional "abort unless `PRIMARY_USER_EMAIL` resolves to exactly one user" precondition would abort on every such empty-table run regardless of whether anything needs backfilling, the same "aborts on every empty-CI-branch run" defect the Multi-User Data Model Retrofit's own migration needed NFR-69 to fix. Zero pre-existing rows is therefore always a clean no-op: the schema change lands, `PRIMARY_USER_EMAIL` is never resolved, and nothing aborts.

**Decision — `whoop_tokens`'s primary key becomes `user_id` itself; the surrogate `id` column and its `check (id = 1)` constraint are dropped, not retained alongside it.** The existing `id smallint primary key default 1 check (id = 1)` exists solely to enforce single-row-ness; a Whoop connection is one-per-user, so `user_id integer primary key references users (id)` **is** the natural key once the table is per-user, and a surrogate `id` would leave `on conflict`'s target ambiguous. The migration drops the `id` column's primary key and `check (id = 1)` constraint (both confirmed live via `pg_constraint` per NFR-82, never assumed) and the `id` column itself, then adds `user_id integer primary key references users (id)`. `saveTokens(userId, tokens)`'s `insert ... on conflict` target becomes `on conflict (user_id)` — this is what makes AC-WT5 ("updated in place, never duplicated") achievable at all; without this decision AC-WT2's "two users each with their own connected `whoop_tokens` row" is unsatisfiable by construction, since a second row could never legally exist.

**Decision — `PRIMARY_USER_EMAIL`/`resolvePrimaryUserId()` is retired from the Whoop sync path, not extended.** Once `whoop_tokens` is user-keyed, the cron loop's source of truth for "which users, and which user owns this pull" is `whoop_tokens` itself — each row already carries the `user_id` to attribute to. The loop's iteration source is a new `listConnectedUsers()` query (`lib/whoop-oauth.ts`, §1) joining `whoop_tokens` to `users` on `user_id`; reusing `resolvePrimaryUserId()` inside the loop would be redundant at best and wrong at worst (it resolves one fixed email, not "whichever user this iteration is for"). `lib/primary-user.ts` is unchanged and stays load-bearing for `/api/ingest/health`, which remains single-user until its own deferred slice (NFR-80).

**Decision — `resolvePrimaryUserId()`'s own failure path in `/api/ingest/health` cannot satisfy a `NOT NULL` `sync_runs.user_id`, and this slice does not paper over that.** AC-PUE2 (shipped, PR #26) requires a `sync_runs` failure row + alert precisely when `PRIMARY_USER_EMAIL` fails to resolve — the one case with no `userId` to write; that block (`tests/integration/ingest.test.ts` lines 383-419) carries its own `AUTO-GENERATED TEST STUB — JerkAI Contract` / `DO NOT EDIT` header and is unmodified by this slice. `sync_runs.user_id` therefore stays **nullable** for this one call site only: the migration's `not null` constraint (AC-WT11) applies to every row this slice's own resolved-attribution paths write, not to the pre-existing config-failure lane AC-PUE2 already owns. `recordSyncRun`'s new parameter is `userId: number | null`, `null` only when called from the `resolvePrimaryUserId()` catch block in `app/api/ingest/health/route.ts` — never from the Whoop sync path, which per NFR-80 no longer calls `resolvePrimaryUserId()` at all and therefore always has a resolved, non-null `userId`. AC-WT11, AC-WT12, and NFR-77 are corrected below to state this exception explicitly rather than claim a blanket zero-null invariant that would break AC-PUE2.

**What this slice is NOT:** no per-user Health Auto Export/ingest changes beyond threading a resolved `userId` into `recordSyncRun`'s two call sites in `app/api/ingest/health/route.ts` so `sync_runs.user_id` can be `not null` everywhere (AC-WT12) — `PRIMARY_USER_EMAIL` keeps attributing ingest rows to Albert, per DL-2026-08-07-a3; no dashboard UI, including any visible "Connect Whoop" button — `/api/whoop/connect` stays reachable only by direct navigation, exactly as today, until "Dashboard Degraded State" adds a CTA; no admin UI; no disconnect/revoke feature; no change to `biometric_readings`, `manual_macro_entries`, or `daily_targets` beyond what the prior slice already shipped.

## 2. Problem statement

A second person can now (per the shipped Multi-User Data Model Retrofit) sign in and see only their own dashboard data — but Whoop is still wired for exactly one account. `whoop_tokens` physically cannot hold a second connection (`id` is checked to equal `1`), the connect/callback flow never learns which user is connecting, the cron sync pulls for one hardcoded user only, and `/status` shows one global, unscoped sync history to every signed-in viewer regardless of whose data it actually is.

## 3. Objective

Any signed-in user can connect their own Whoop account, the daily cron pulls and attributes data correctly for every connected user independently (one user's failure never blocks another's), and each user sees only their own connection state and sync history. Success = a second invited friend can complete "Connect Whoop" (once its UI CTA ships in a later slice) and see their own Whoop-sourced dashboard data, with zero risk of it mixing with Albert's.

## 4. Functional Requirements — user-centered acceptance criteria

Written as testable Given/When/Then. New id prefix **AC-WT** (Whoop tenancy), numbered from 1 — no collision with any existing jerkai prefix (`AC-D`, `AC-N`, `AC-W`, `AC-M`, `AC-PD`, `AC-AB`, `AC-AU`, `AC-MU`), verified against every jerkai Build PRD in the vault this session.

* **AC-WT1 (bare case)** — Given zero rows in `whoop_tokens` (nobody has ever connected), When the cron sync runs, Then it completes successfully having processed zero users, writes no `biometric_readings` or `whoop_workouts` rows, records no misleading failure, and sends no alert — the app-wide "not connected" shortcut response is retired in favor of this now-legitimate empty-loop state.
* **AC-WT2** — Given two users each with their own connected `whoop_tokens` row, When the cron sync runs, Then each user's pulled `biometric_readings` and `whoop_workouts` rows are attributed to their own `user_id` — never crossed, even where both users have data for the identical metric and date.
* **AC-WT3 (failure isolation)** — Given two connected users where one user's Whoop API call fails (e.g. token refresh error, API outage) during the run, Then the other connected user's sync still completes, is recorded as its own independent outcome, and is not marked failed or skipped because of the first user's error.
* **AC-WT4 (connect/callback binding)** — Given user A initiates `/api/whoop/connect` (setting both the state and user-id cookies) and, before the callback completes, the active session in that same browser becomes user B's, When Whoop's redirect reaches `/api/whoop/callback`, Then the callback is refused (same shape as a state mismatch — restart from `/api/whoop/connect`) rather than attributing the resulting tokens to user B.
* **AC-WT5** — Given a user who already has a connected `whoop_tokens` row, When they complete the connect flow again (re-consent/reconnect), Then their existing row is updated in place (same `user_id`), never duplicated.
* **AC-WT6** — Given a signed-in user with no `whoop_tokens` row, When `getFreshAccessToken(userId)` is called for their id, Then it returns `null` — the existing "never connected" behavior (`lib/whoop-oauth.ts:154-166`), now keyed per user rather than app-global.
* **AC-WT7** — Given a cron run covering two connected users, Then `sync_runs` gains one row per user for that run (or the equivalent per-user record) — never one row conflating both users' outcomes into a single status.
* **AC-WT8** — Given two users each with their own sync history, When either loads `/status`, Then they see only their own sync history — never the other user's, even though `sync_runs` now holds both. Given a signed-in user with **zero `sync_runs` rows of their own** while another user has one or more, `/status` shows that user's own empty ("never") state for every source, never the other user's history.
* **AC-WT9** — Given a connected user's sync fails, When the failure alert is sent, Then its body names that user (by email), so Albert's inbox can distinguish whose sync failed when more than one user is connected.
* **AC-WT10 (migration, whoop_tokens)** — Given **zero rows in `whoop_tokens`** (true of every disposable CI branch, and of production before Albert's first Whoop connection), When the production migration runs, Then it completes successfully as a no-op backfill — the schema change (`user_id` column, PK swap) lands, and `PRIMARY_USER_EMAIL` is never required to resolve. Given **exactly one pre-existing `whoop_tokens` row** (`id = 1`) and the `PRIMARY_USER_EMAIL` configured for this environment, When the production migration runs, Then that row is backfilled to `PRIMARY_USER_EMAIL`'s resolved `user_id` — not to "the sole row in `users`" — and, only in this case (a row exists to backfill), the migration aborts without modifying `whoop_tokens` if `PRIMARY_USER_EMAIL` is unset or resolves to zero or more than one `users` row.
* **AC-WT11 (migration, sync_runs)** — Given **zero pre-existing `sync_runs` rows**, When the production migration runs, Then it completes as a no-op backfill — `sync_runs.user_id` is added and no `PRIMARY_USER_EMAIL` resolution is required. Given **one or more pre-existing `sync_runs` rows** (all currently attributable to Albert's own syncs), When the production migration runs, Then they are backfilled to the same `PRIMARY_USER_EMAIL`-resolved `user_id` as AC-WT10, and `sync_runs.user_id` is nullable, `not null` only for every row attributable to a resolved user — the pre-existing `resolvePrimaryUserId()`-failure lane (AC-PUE2, `tests/integration/ingest.test.ts` lines 383-419) is the sole exception and remains unaffected by this migration; the migration aborts under the same conditional precondition as AC-WT10 (triggered only when rows actually exist to backfill).
