## 0. Scope & Sequencing Note (read first)

### 0.1 Why this slice, why now

Albert uploaded a Claude Design mockup redesigning `/status` into a categorized, card-based "Data" page with real Connect actions, and confirmed (this session) that the build is a full feature build, not a restyle: the categorized cards, the Connect actions, and the Apple Health setup modal must be real functionality, not a reskin of the existing three-line list.

The single most important fact this session had to establish before drafting any AC was whether Whoop and Withings already have shipped, working OAuth connect infrastructure, or whether this slice would need to build OAuth from scratch. **It does not need to build OAuth from scratch, for either source.** Confirmed live this session: `app/api/whoop/connect/route.ts` (38 lines) and `app/api/withings/connect/route.ts` (38 lines) both exist, are both fully implemented (state-cookie CSRF protection, session-user binding, redirect to the provider's authorize URL), and both stay behind the Auth.js session gate exactly as `proxy.ts`'s matcher comment states ("Exact match, so `/api/whoop/connect` STAYS gated"; the identical sentence for Withings). `grep -rn "api/withings/connect\|api/whoop/connect" app` (this session) found **zero** references anywhere in `app/` outside the two connect routes' own files and their sibling callback routes' error strings — meaning **neither route has ever had a UI entry point**. This matches [[JerkAI - Decision Log]] `DL-2026-08-07-a4`'s own framing of the still-unauthored "Dashboard Degraded State" PRD as the place a "Connect Whoop" CTA was expected to eventually ship, and Whoop Multi-Tenancy's own §0 ("`/api/whoop/connect` remains reachable only by direct navigation, exactly as it is today"). So this slice's Connect buttons for Whoop and Withings are thin `<a href>` links into already-shipped, already-tested infrastructure — the "biggest scope risk" this session was asked to resolve turns out to shrink the slice, not grow it, and this is the **first surface in the entire app to give either connect route a real UI entry point.**

Fitdays is a different story, confirmed by direct read of `app/api/ingest/health/route.ts`, `.env.example`, and `lib/primary-user.ts` this session, and it is the second-biggest grounding correction this PRD makes to the mockup. Fitdays/Apple Health data reaches JerkAI through `POST /api/ingest/health`, authorized by **one single, server-configured shared secret** (`HEALTH_EXPORT_SHARED_SECRET`, `.env.example:5-7`: "Generate: `openssl rand -hex 32`" — one value, set once, by Albert, in Vercel) and attributed to whichever user `PRIMARY_USER_EMAIL` resolves to (`lib/primary-user.ts#resolvePrimaryUserId`). There is no per-user API key, no key-generation endpoint, and no mechanism anywhere in this repo that could produce the mockup's modal copy — *"Paste in the API key we generate for your account."* Whoop Multi-Tenancy's own §0 confirms this is a known, deliberate limitation, not an oversight: *"no per-user Health Auto Export ingest tokens or any Fitdays/Apple-Health multi-tenancy (still deferred, DL-2026-08-07-a3) — `/api/ingest/health` keeps its single-secret, `PRIMARY_USER_EMAIL`-attributed shape."* This slice does not build per-user Fitdays connect infrastructure (that would be new backend machinery well past "wire up existing flows," and no PRD has ever scoped it). Instead, the Fitdays modal is corrected to be **honest about what exists today**: static setup instructions with no per-account key claim, and no server round-trip when "I've set it up" is clicked (§0.4, OQ-3).

### 0.4 Decision — "Connected" tag and "has sync history" are two independent facts about a card, not one boolean gating the other

**Considered:** (A) follow the mockup literally — a card is either "connected" (shows sync history + a small "via {method}" label, no Connect action) or "not connected" (shows connect-prompt copy + a Connect action, no sync history at all), matching its `sc-if`/`sc-if` either/or; (B) decouple the two — a "Connected"/"Not connected" tag reflects whether a live OAuth token (Whoop/Withings) or primary-user identity (Fitdays) exists for the signed-in user, shown independently of whether `sync_runs` has any history; the sync-history lines render exactly as they do today, unconditionally, and the Connect action shows only when not connected.

**Rejected A**, for two independent reasons found by direct grounding this session, not by preference: (1) `tests/integration/status.test.ts`'s `AC-ST2`/`AC-ST3` blocks (Status Sync Times — Local Timezone, shipped, `DO NOT EDIT`) seed only a `sync_runs` row — no `whoop_tokens`/`withings_tokens` row — and require the sync-history line to render with a real, parseable ISO instant. Under model (A), that fixture's source would read "not connected" (no token row) and the connect-prompt branch would render instead, with no sync-history line at all — silently breaking two shipped, `DO NOT EDIT`-headered tests with no PRD authorization to touch them, which Hard Rule 5/6 and `jerkai-spec`'s own discipline forbid doing quietly. (2) Model (A) also produces a materially worse user-facing state for the ordinary "just connected via OAuth, cron hasn't run yet" case: a user who completes Whoop OAuth and lands back on `/data` before the next daily cron run has a `whoop_tokens` row but zero `sync_runs` rows — under (A) they would see... nothing coherent, since the mockup's fixture never actually models "connected AND zero history" (its own fixture always pairs `connected: true` with a non-null `lastSuccess`). Model (B) handles this cleanly and for free: "Connected" tag (from the token row), "Last successful sync: never" (from zero `sync_runs` rows, exactly today's existing fallback text) — both true, both rendered, no contradiction.

**Build B.** The practical shape: each card independently computes (a) a Connected/Not-connected tag — Whoop/Withings from token-row existence, Fitdays from primary-user identity (§0.5) — and (b) its sync-history content — exactly `app/status/page.tsx`'s existing per-source block, unconditional, unmodified. A Connect action (link or button) renders only when (a) is Not-connected.

### 0.5 Decision — Fitdays' "Connected" tag reflects primary-user identity, not sync history

**Considered:** (A) derive Fitdays' connected state from `resolvePrimaryUserId()` — "Connected" iff the signed-in user *is* the user this app's single ingest pipe is currently configured to attribute rows to; (B) derive it from whether this user has ever had a successful `fitdays` `sync_runs` row — a pure activity proxy, no primary-user lookup needed.

**Rejected B:** it misrepresents "connected" as an activity metric rather than an identity/configuration fact. A user who is correctly the configured primary user, the day after being invited, before Health Auto Export has ever run, would read "Not connected" under (B) even though nothing is actually wrong or unconfigured for them — indistinguishable, from the UI, from a user who structurally can never receive Fitdays data at all (every other invited user, today, per DL-2026-08-07-a3/Whoop Multi-Tenancy §0's confirmed limitation that Fitdays ingest is not yet multi-tenant). **Build A** — it is the honest, verifiable-from-source signal: is this account the one Fitdays data can currently reach at all. `resolvePrimaryUserId()` throws when `PRIMARY_USER_EMAIL` is unset or resolves to zero/more-than-one `users` rows (`lib/primary-user.ts:10-17`, read live this session) — every call site on this page wraps it in try/catch and treats **any** non-single-match outcome identically as "not connected" (never a page crash — §5 NFR-122). This fail-closed behavior is not merely defensive: it is load-bearing for the four pre-existing `DO NOT EDIT` blocks' own test fixtures, none of which seed a `users` row matching whatever `PRIMARY_USER_EMAIL` the CI environment configures — under a naive unhandled-throw implementation, every one of those four blocks' page renders would 500 on this slice's own new Fitdays-connected-check code, an entirely avoidable regression this decision exists to prevent.

### 0.6 Decision — category and method-label metadata lives outside `lib/sources.ts`, not inside it

**Considered:** (A) widen `READING_SOURCES`/`ACTIVE_SYNC_SOURCES` (`lib/sources.ts`, 19 lines, read in full this session) from flat `readonly string[]` to a richer per-source object carrying category/method/display-name; (B) add a small, separate, page-local mapping (inline in `app/data/page.tsx`, or a new colocated module) carrying that same display metadata, leaving `lib/sources.ts`'s existing exported shape byte-unchanged.

**Rejected A:** `ACTIVE_SYNC_SOURCES` is iterated as a flat string array by this same page today, and `ReadingSource` (its derived type) is consumed by `lib/sync-runs.ts`'s `recordSyncRun` signature and every ingest/sync route's call sites — widening its element shape is a real, unbudgeted ripple into files this slice has no reason to touch (Hard Rule against silent scope expansion, [[JerkAI - Build Failure Ledger]] `FM-08`). **Build B.** The category groupings ("Scale": Fitdays, Withings; "Performance": Whoop), the per-source method label ("Apple Health" vs. "OAuth"), and the per-source display name ("Fitdays", "Withings", "Whoop") are presentation-only facts with exactly one consumer (this page) — they belong next to that consumer, not in the shared source registry.

### 0.7 What this slice is NOT

No change to any `/api/whoop/*`, `/api/withings/*`, or `/api/ingest/health` route — this slice reads token existence and links to already-shipped connect routes; it writes nothing to `whoop_tokens`, `withings_tokens`, `sync_runs`, or `biometric_readings`, and calls no third-party API. No change to `lib/whoop-oauth.ts`'s or `lib/withings-oauth.ts`'s *existing* exported functions — each file gains exactly one new, additive, read-only export (§1). No disconnect/revoke UI for any source (none exists today for Whoop or Withings either — not a new gap this slice opens). No per-user Fitdays/Apple Health ingest token, key-generation endpoint, or any other new backend machinery for Fitdays — the modal is informational only (§0.1, §8 OQ-3). No dashboard-surface ("/", "/weekly", "/daily") Connect CTA — that is the separate, not-yet-authored "Dashboard Degraded State" PRD (DL-2026-08-07-a4); this slice does not overlap or conflict with it, since it touches a different page entirely, but it is worth naming explicitly since this slice ships the first *any* functional Connect CTA in the app (§8 OQ-7). No schema migration — "Connected" is derived entirely from existing tables (`whoop_tokens`, `withings_tokens`, `users`), no new column or table.

**This is one coherent slice, not two.** All three sources' Connect actions are thin, already-shippable UI wiring against infrastructure or a documented limitation this session verified directly — none of the three requires new OAuth logic, a new migration, or genuinely separable review risk from the other two.

### 0.8 Decision — extend the Weekly/Daily nav-highlight mechanism to all five nav links: Data, Log Meal, and Targets (added this reconciliation, 2026-08-30; corrected same session)

## 2. Problem statement

`/status` (`app/status/page.tsx`) shows a flat, unstyled three-line list — one per `ACTIVE_SYNC_SOURCES` entry (`fitdays`, `whoop`, `withings`) — with no grouping, no indication of *how* a source connects (OAuth vs. Apple Health export), and, critically, no way to actually connect one. Two of the three sources (Whoop, Withings) already have fully built, tested, per-user OAuth connect infrastructure (`app/api/whoop/connect/route.ts`, `app/api/withings/connect/route.ts`) that has never had a UI entry point anywhere in the app — a signed-in user with a `withings_tokens` gap has no way to close it except typing `/api/withings/connect` into the address bar by hand. The third (Fitdays) has no per-user connection concept at all — it is a single, server-configured ingest pipe attributed to whichever user `PRIMARY_USER_EMAIL` names — a real architectural fact the page's current design does not surface and a future redesign (like the uploaded mockup) could easily misrepresent.

## 3. Objective

A signed-in user visiting `/data` sees their biometric data sources grouped by category, each card showing how it connects, whether it is connected, when it last synced, and — for a not-yet-connected OAuth source — a working link that actually starts that connection; for Fitdays, a modal with accurate, honest setup instructions. Success = a single testable condition: a signed-in user with no `withings_tokens` row can click "Connect" on the Withings card and land, via a real 302, on Withings' own OAuth consent screen — the first time this has ever been possible from inside the app's UI.

## 5. Non-Functional Requirements (FDE)

All prior NFRs (1–119, the live high-water mark as of this session — verified directly by grepping every `Career/Projects/JerkAI - Build PRD*.md` file for `NFR-[0-9]+` and cross-checking the same pattern against `docs`/`tests`/`lib`/`app` in the repo, both converging on 119; **not** trusted from `docs/codebase.md`'s own citation of 119, which is corroborating, not the source of truth) remain in force where applicable. The following are additive, numbered from 120.

* **NFR-120 — Connected-state checks are direct, read-only existence queries, never a call that refreshes or re-persists a token.** The new Whoop/Withings existence-check functions (§1) query `whoop_tokens`/`withings_tokens` directly (e.g. `select 1 from whoop_tokens where user_id = $1 limit 1`) and never call, or route through, `getFreshAccessToken` — which proactively refreshes and re-saves tokens as a side effect of being called (confirmed live, `lib/whoop-oauth.ts:151-168`, this session). ## 8. Open Questions

* **OQ-1 (non-blocking, default provided)** — Should `/status` continue to work at all after the rename, or is a clean 404 acceptable? Default: yes, redirect `/status` → `/data` (AC-DS2) — cheap (one small file), avoids breaking any existing bookmark or browser-history entry any allowlisted user may have saved, and matches this app's own precedent of a plain `redirect()` call in a Server Component (the page's own existing `redirect("/signin")`, confirmed live). Revisit only if Albert prefers a bare 404 instead.
* **OQ-2 (non-blocking, default provided)** — Is primary-user identity really the right signal for Fitdays' "Connected" tag, given it will make every non-primary user permanently read "Not connected" regardless of anything they do? Default: yes (§0.5) — this is not a bug this slice introduces, it is an honest reflection of a real, already-decided, already-documented architectural limitation (DL-2026-08-07-a3); the alternative (deriving from sync history) would make the tag lie about a user who is correctly configured but simply hasn't synced yet. Revisit only alongside a future decision to build real per-user Fitdays connect.
* **OQ-3 (non-blocking, default provided)** — What should happen server-side when "I've set it up" is confirmed for Fitdays? Default: **nothing** — no network request, no persisted state (AC-DS16/NFR-123). Under the current single-secret, primary-user-attributed architecture there is no per-user "setup confirmed" fact to record; the card's Connected tag is already correctly driven by primary-user identity (OQ-2) and its sync-history line already updates itself the moment Health Auto Export's next export actually lands, with no confirmation step needed. This is the single largest deviation from the mockup's own script (which wires "I've set it up" to `connectOAuth`, a state-mutating call) — flagged prominently per this session's own instructions, since it is a genuine, considered scope correction, not an oversight.
* **OQ-4 (non-blocking, default provided)** — Should the modal display the actual value of `HEALTH_EXPORT_SHARED_SECRET` so the user doesn't have to go find it elsewhere? Default: no (AC-DS14/NFR-123) — it is a genuine secret (`.env.example`'s own comment: "Generate: `openssl rand -hex 32`"), and rendering it into a client-visible page for a value that already lives in the phone-side Health Auto Export app once configured is an unforced security surface this slice does not need to open. Revisit only if Albert explicitly wants a "reveal secret" flow, which would need its own NFR treatment.
* **OQ-5 (non-blocking, default provided)** — Rename the test file (`status.test.ts` → `data.test.ts`) or leave its name as-is despite the route move? Default: rename (§1) — leaving a file literally named `status.test.ts` covering a page that no longer exists at that path is confusing for the next PRD's own required-reading pass, and a `git mv` plus one import-line edit is the entire cost.
* **OQ-6 (non-blocking, default provided)** — Should Whoop/Withings' method label read "OAuth" (as the mockup shows) or something more specific ("Whoop OAuth", "Withings OAuth")? Default: the mockup's plain "OAuth" — it is a category label distinguishing *how* a source connects (OAuth vs. Apple Health export) from *what* it's called (the source name, already shown separately on the same card), so naming the provider a second time in the method label is redundant.
* **OQ-7 (non-blocking, default provided, informational)** — Does this slice conflict with the still-unauthored "Dashboard Degraded State" PRD (DL-2026-08-07-a4), which is expected to add its own "Connect Whoop" CTA on the dashboard? Default: no conflict — that PRD's scope is the dashboard surfaces (`/`, `/weekly`, `/daily`); this slice's Connect actions live only on `/data`. Worth flagging explicitly because this slice ships the *first* functional Connect CTA anywhere in the app — whoever authors that future PRD should read this one first rather than re-deriving the OAuth-link-into-existing-infrastructure pattern from scratch.
