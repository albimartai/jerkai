## 0. Scope & Sequencing Note (read first)

Every row in `biometric_readings`, `manual_macro_entries`, and `daily_targets` is unscoped today — verified this session directly against every migration file (`migrations/1783533131865_create-biometric-readings.js`, `migrations/1784567579158_create-manual-macro-entries-and-daily-targets.js`) and every read/write path (`lib/readings.ts`, `lib/meal-entries.ts`, `lib/targets.ts`, `lib/dashboard/data.ts`): none of the three tables has a user column, and none of the six read/write functions over them (`upsertReading`, `saveMealEntry`/`fetchMealEntriesForDate`/`updateMealEntry`/`deleteMealEntry`/`fetchDailyCalorieTotals`, `saveTarget`/`fetchTargets`, `fetchDashboardData`) takes any per-user argument. `updateMealEntry` and `deleteMealEntry` in particular operate on `id` alone with no ownership check at all. This slice closes that: it is the thing DL-2026-08-07-a2 names as the precondition for adding a second email to `ALLOWLISTED_EMAILS` — until it ships, any second allowlisted person would reach every one of Albert's rows.

**A real per-request user identity does not exist yet either — verified this session.** Auth.js's Neon adapter already creates a real, multi-row-capable `users` table (`migrations/1783629665741_create-authjs-tables.js`, `id serial primary key`), and the installed `@auth/core@0.41.2`'s default JWT flow already sets the token's `sub` claim to the adapter's `users.id` on sign-in, for the email/magic-link provider this app actually uses (confirmed at `node_modules/@auth/core/lib/actions/callback/index.js:177`, the `provider.type === "email"` branch: `sub: loggedInUser.id?.toString()` — not the unrelated Credentials-provider branch at line 251, which this app never exercises). But the same package's default session assembly (`node_modules/@auth/core/lib/actions/session.js:37-40`) builds `session.user` as `{ name, email, image }` only — no `id` — and `auth.ts`'s `callbacks` object (verified this session) defines only `authorized` and `signIn`, no `session` callback to copy `token.sub` across. **Every call to `auth()` anywhere in the app today gets a session with no usable database identity in it.** Wiring that through is in scope here, not a separate slice, because nothing else in this PRD can be scoped by user without it.

**Decision — Albert's existing data becomes user 1 through the normal path, no special-casing (DL-2026-08-07-a7).** The migration backfills existing rows onto whichever row already exists in `users` (Albert's, created the first time he ever signed in) rather than a hardcoded id or a synthetic "owner" row. **Decision — the migration's precondition treats zero rows as safe-no-op, not abort (extends DL-2026-08-07-a2's safety framing to the migration itself; corrects an earlier draft that treated "anything other than exactly one row" as the abort condition).** DL-2026-08-07-a2 guarantees at most one real user exists when this migration runs (no second email has been added yet — see PRD 1 §0/NFR-66). But "at most one" includes zero — which is exactly what every disposable CI branch looks like: `scripts/ci/neon-branch.mjs` creates a genuinely empty database (verified this session), so `users` holds 0 rows every time `npm run migrate:ci` runs in CI (`.github/workflows/ci.yml`'s "Run migrations from an empty database" step, which always runs before "Integration tests"). If the migration aborted on zero rows, it would abort on every CI run, forever, and `user_id` would never exist on any disposable branch. The migration's actual precondition is therefore: **more than one row in `users` aborts** the transaction without modifying any table; **zero or one row** proceeds (zero rows = nothing to backfill, schema change lands as a no-op backfill; one row = Albert's row, backfill runs). This is the same "never guess, fail loudly" discipline `lib/dashboard/data.ts`'s null-vs-empty handling and `jerkai-mcp`'s coverage nulls already follow elsewhere in this product — it guards against guessing among *multiple* candidate owners, not against an empty table.

**What this slice is NOT:** no Whoop schema/route changes beyond the one `upsertReading` call site inside `/api/whoop/sync` that this slice's signature change forces to update — `whoop_tokens` stays the existing singleton and `whoop_workouts` stays unscoped, both explicitly deferred to "Whoop Multi-Tenancy"; no per-user Health Auto Export tokens (DL-2026-08-07-a3 — the ingest route keeps single-user attribution, just resolved by email lookup instead of an implicit global scope); no dashboard UI change (a separate PRD); no admin UI; and, operationally, no second email actually added to `ALLOWLISTED_EMAILS` as part of this slice — that is Albert's manual step afterward, once the production migration is confirmed live (mirroring PRD 1's NFR-66).

## 2. Problem statement

Every row in the three tables this slice touches is reachable by any session that passes the sign-in gate, because no row carries a user, no query filters by user, and two write paths (`updateMealEntry`, `deleteMealEntry`) don't even check an id's owner before mutating it. Auth.js's session object carries no database user id to filter by even if the queries wanted one. A second allowlisted person cannot safely exist until both gaps close.

## 3. Objective

Every read and write over `biometric_readings`, `manual_macro_entries`, and `daily_targets` is scoped to the signed-in session's `user_id`, sourced from a real, tested session identity. Albert's existing data is backfilled onto his own `users` row with no hardcoded identity anywhere in schema or code. Success = a second person could be added to `ALLOWLISTED_EMAILS` today and see only their own (empty) data, never Albert's.

## 4. Functional Requirements — user-centered acceptance criteria

Written as testable Given/When/Then. New id prefix **AC-MU** (multi-user), numbered from 1 — no collision with `AC-D`, `AC-N`, `AC-W`, `AC-M`, `AC-PD`, `AC-AB`, or `AC-AU` (verified against every jerkai Build PRD in the vault this session, including the now-shipped `AC-AU` series).

* **AC-MU1 (bare case)** — Given a signed-in user with zero rows of their own in `biometric_readings` (regardless of whether other users' rows exist), When `fetchDashboardData` runs for them, Then it returns an empty axis and `latestDay: null` for them specifically — the existing empty-state behavior (`lib/dashboard/data.ts:74-76`), never falling through to another user's rows.
* **AC-MU2** — Given two users each with a `biometric_readings` row for the identical `(source, metric, reading_date)` triple, When each is read back, Then both rows coexist and each user sees only their own value — the widened `(user_id, source, metric, reading_date)` uniqueness (§5, NFR-67) is what makes this possible; today's `(source, metric, reading_date)` constraint would collide the two.
* **AC-MU3** — Given two users where user B has a more recent `biometric_readings` reading than user A, When `fetchDashboardData` runs for user A, Then user A's computed axis end date is derived only from user A's own rows — user B's newer reading never shifts it (closes the CTE-scoping landmine at `lib/dashboard/data.ts:48-59`, §1).
* **AC-MU4** — Given a signed-in user, When they log a meal, edit or delete it, view a day's entries, or view the calorie strip, Then only rows carrying their own `user_id` are written, read, updated, or deleted — even where another user has an entry on the identical `entry_date`. Given a signed-in user with **zero entries of their own** on a date another user has entries for, viewing that day (`fetchMealEntriesForDate`) and the calorie strip (`fetchDailyCalorieTotals`/`fetchCalorieSeries`) show that user's own empty state, never the other user's entries or total.
* **AC-MU5 (cross-user security)** — Given a `manual_macro_entries` row owned by user A, When user B calls `updateMealEntry` or `deleteMealEntry` naming that row's `id`, Then the result is indistinguishable from the id not existing at all (`updateMealEntry`'s existing `{ ok: false, reason: "not_found" }`; `deleteMealEntry`'s existing `{ deleted: false, entry: null }`), and the row is neither modified nor deleted.
* **AC-MU6** — Given a signed-in user, When they save or fetch daily targets, Then only rows carrying their own `user_id` are written or returned, independent of any other user's targets. Given a signed-in user with **zero targets of their own** while another user has one or more targets, `fetchTargets` for the first user returns an empty list, never the other user's targets.
* **AC-MU7** — Given a signed-in session (magic-link verified, per the shipped allowlist gate), When any code calls `auth()`, Then `session.user.id` resolves to that user's real, stable `users.id` — verified by a unit test of the new `session` callback in `lib/auth-callbacks.ts`, exercised without the full NextAuth adapter/provider setup (matching `authorized`/`signIn`'s existing test pattern).
* **AC-MU8 (migration safety)** — Given a database where the `users` table holds **more than one row** at migration time, When the production migration's backfill step runs, Then it aborts without modifying `biometric_readings`, `manual_macro_entries`, or `daily_targets`, and no column is left partially backfilled.
* **AC-MU9 (migration correctness)** — Given a database where `users` holds **zero or exactly one row**, When the migration runs, Then the schema change (columns added, constraint widened) lands, any existing row is backfilled to that sole user if one exists (a no-op backfill if zero), and `user_id` can then be made `not null` with zero remaining `null` values — this is also the path `npm run migrate:ci` exercises on every disposable branch (`users` starts at 0 rows there, per `scripts/ci/neon-branch.mjs`), and it must succeed there, not merely against a hand-seeded one-row fixture.
* **AC-MU10** — Given a request to `/api/ingest/health` (no session — machine-to-machine, `x-api-key`-gated), When a payload is accepted and rows are upserted, Then every resulting `biometric_readings` row is attributed to the user resolved by looking up `users` for the email configured in `PRIMARY_USER_EMAIL` at request time — never a hardcoded numeric id, and the request fails closed (no rows written) if that email resolves to zero or more than one `users` row.
* **AC-MU11** — Given a Whoop sync run (`/api/whoop/sync`, no session — `CRON_SECRET`-gated), When readings are upserted via `upsertReading`, Then they are attributed using the same `PRIMARY_USER_EMAIL` resolution as AC-MU10; the sync's `whoop_workouts` writes (via `upsertWorkout`) are unchanged and remain unscoped, per §0.
* **AC-MU12 (migration continuity, bare pre-migration case)** — Given Albert's pre-existing `biometric_readings`, `manual_macro_entries`, and `daily_targets` rows as they exist today (single-user, no `user_id`), When the production migration's backfill runs and Albert then signs in and loads the dashboard, a day's meal entries, and his targets, Then `fetchDashboardData`, `fetchMealEntriesForDate`, and `fetchTargets` return exactly the same rows he had before the migration — nothing is dropped, orphaned, or made invisible by the backfill scoping his data onto his own `user_id`.

## 5. Non-Functional Requirements (FDE)

All prior NFRs remain in force; the following are additive, continuing jerkai's numeric series after **NFR-66** (Extend Sign-In Allowlist — verified as the current live high-water mark this session; a stale, never-built `NFR-63`–`NFR-80` allocation referenced in `jerkai-mcp`'s Slice 1 PRD header does not collide, per that PRD's own note that the allocation "was never built and no longer resolves").

* **NFR-67 — Every query over the three retrofitted tables is scoped by `user_id`; no code path returns or mutates a row belonging to a different user.** This is the overarching invariant AC-MU1–AC-MU6 each exercise a piece of, enumerated by construction (FM-07) rather than asserted as an unstated property — every site below must gain a `user_id` filter or column:
  - `lib/readings.ts` — the cumulative-read select (lines 34-38) and the upsert `insert ... on conflict` (lines 49-58), both currently keyed only on `(source, metric, reading_date)`.
  - `scripts/seed-dev.mjs` — the raw `insert into biometric_readings` (lines 14-20); see §1.
  - `lib/meal-entries.ts` — `saveMealEntry`'s insert (lines 45-51); `fetchMealEntriesForDate`'s select (lines 91-100); `updateMealEntry`'s existing-row select and update (lines 121-156, both currently keyed on `id` alone — closes the AC-MU5 security gap, not just scoping); `deleteMealEntry`'s delete (lines 163-171, same `id`-alone gap); `fetchDailyCalorieTotals`'s aggregate select (lines 197-209).
  - `lib/targets.ts` — `saveTarget`'s insert (lines 19-27); `fetchTargets`'s select (lines 39-61), which today has **no `WHERE` clause at all** and returns every user's targets.
  - `lib/dashboard/data.ts` — the `dashboard_rows` CTE (lines 48-54) itself, not just the outer `select` that reads it (NFR-68 covers the axis-date consequence of getting this one wrong).
  Any site touching these tables that is *not* in this list and is discovered during the build must be added here before the PR, not scoped silently — the build agent flags it in the session close-out (§7) rather than treating this list as exhaustive-by-assumption.
* **NFR-68 — A user's "latest reading day" is always derived from that user's own rows, never from global data.** Applies wherever `fetchDashboardData` or any future consumer computes an axis boundary from `biometric_readings` (backs AC-MU3).
* **NFR-69 — The production migration's backfill is all-or-nothing against its at-most-one-user-row precondition (zero or one row proceeds, more than one row aborts); it never partially backfills and never guesses an owner among multiple candidates** (backs AC-MU8/AC-MU9). The precondition check and the backfill run in the same transaction as the schema change, so a failed precondition leaves the database exactly as it was, not half-migrated. Zero rows is not a failed precondition — it is the state of every disposable CI branch, and the migration must succeed (as a no-op backfill) against it.
* **NFR-70 — `session.user.id` is derived from the JWT's `sub` claim (already set by Auth.js's default `jwt` callback to the adapter's `users.id`, confirmed this session against `node_modules/@auth/core`) via a `session` callback colocated in `lib/auth-callbacks.ts`, unit-testable without the full NextAuth adapter/provider setup** — the same extraction pattern `authorized` and `signIn` already use (`auth.ts:43-44`'s own comment: "Access-control decisions live in lib/auth-callbacks.ts (unit tested there, without the adapter/provider setup this file needs)."; and `lib/auth-callbacks.ts:1-4`'s own header: "...auth.ts wires these into its config unchanged — keep the logic here, not there."). The `Session`/`JWT` types are augmented (a new file) so `session.user.id` is a typed, non-optional value everywhere it is read — not a cast, not an `any`. **The augmented type is `string`, not `number`** — the JWT `sub` claim is `loggedInUser.id?.toString()` (§0, `@auth/core`'s email-provider branch), while the underlying `users.id` column is `serial` (integer, per `migrations/1783629665741_create-authjs-tables.js`). Every call site that uses `session.user.id` to parameterize a query against `user_id` (an integer column on all three retrofitted tables) must explicitly convert with `Number(session.user.id)` at the point of the query call — never pass the string straight into a tagged-SQL template and rely on implicit coercion, and never change the column type to match the string instead.
* **NFR-71 — Machine-to-machine attribution (ingest, Whoop sync) never hardcodes a numeric user id literal in source.** Both resolve a configured email to a `user_id` at request/run time, so the mechanism generalizes cleanly when per-user tokens or OAuth eventually replace single-user attribution (DL-2026-08-07-a3) without a second retrofit of the resolution logic itself.
* **NFR-72 — The exact system-generated unique-constraint name being dropped on `biometric_readings` is confirmed against the live schema at migration-authoring time (e.g. via `pg_constraint`), never assumed from Postgres's default naming convention** (§1).

## 8. Open Questions

* **OQ-1 (default: new dedicated env var `PRIMARY_USER_EMAIL`, resolved to a `user_id` at request time).** How should the ingest and Whoop-sync routes know which user to attribute rows to, given neither has a session? Considered: (a) a new `PRIMARY_USER_EMAIL` env var, looked up against `users` per request — chosen as the default, because it keeps identity data-driven (no numeric id baked into source, per NFR-71) and reuses the email-as-identity pattern `ALLOWLISTED_EMAILS` already established; (b) a literal numeric `PRIMARY_USER_ID` env var — rejected as default because a raw integer in Vercel config is opaque and easy to mis-set with no way to catch a typo except a downstream foreign-key failure, whereas an unresolvable email fails closed loudly and legibly; (c) inferring the target from the sole current `ALLOWLISTED_EMAILS` entry — rejected as default because it silently couples ingest/Whoop attribution to sign-in eligibility, two concerns that should be able to change independently (e.g., Albert could someday be allowlisted under a different email than his ingest identity). Revisit once per-user tokens replace this (DL-2026-08-07-a3) — at that point `PRIMARY_USER_EMAIL` is removed, not repurposed.
* **OQ-2 (default: one migration file for all three tables).** Should the schema change ship as one migration touching all three tables, or split per table? Default: one file — the three tables share one precondition check and one backfill transaction (NFR-69), and splitting them risks a partially-applied retrofit if one file lands without the others. Revisit only if migration review finds the combined file unwieldy. **Resolved this session: one file** (`migrations/1786637399180_add-user-id-to-biometric-readings-manual-macro-entries-and-daily-targets.js`).
* **OQ-3 (default: no cascade rule; FK defaults to `RESTRICT`).** Should the `user_id` foreign key specify `ON DELETE CASCADE` or similar? Default: no explicit rule (Postgres's default `NO ACTION`/`RESTRICT`) — no user-deletion feature exists yet, so no AC exercises this, and choosing a cascade behavior now would be speculative. Revisit when/if a user-deletion or account-closure feature is ever specified. **Resolved this session: no explicit `ON DELETE` clause**, matching the default.
