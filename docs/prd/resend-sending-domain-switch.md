## 0. Scope & Sequencing Note (read first)

`auth.ts`'s Resend provider and `lib/alerts.ts`'s `sendSyncFailureAlert` both send from Resend's shared testing domain, `onboarding@resend.dev`. Each file carries a code comment that already names the constraint and the fix, written when this app had exactly one possible recipient: `auth.ts:26` — *"onboarding@resend.dev delivers only to the Resend account owner — ... fine here because the allowlist restricts sign-in to that one address anyway"* — and `lib/alerts.ts:24-26` — *"onboarding@resend.dev delivers only to the Resend account owner's address — fine for a single-user app; switch to a verified jerkai.app sender when the domain is added to Resend."* Neither comment was wrong when written. Both describe a condition — `ALLOWLISTED_EMAILS` holding exactly one address — that stopped being true this session: a second, real address was added to `ALLOWLISTED_EMAILS` and the app redeployed (this session, following [[JerkAI - Build PRD - Extend Sign-In Allowlist]]'s own mechanism), and the data-isolation retrofit that decision `DL-2026-08-07-a2` gated a second address on has since shipped and been independently confirmed live in production — twice, per [[JerkAI - Build Failure Ledger]]'s 2026-08-13 and 2026-08-19 retro entries (the *Multi-User Data Model Retrofit* and *Whoop Multi-Tenancy* PRs). So the allowlist side of "invite a second person" is done and safe. The email side is not: this session found no reference anywhere in the repo to a verified sending domain, a DNS record, or Resend domain configuration — only these same two sandbox-domain literals. A second allowlisted person requesting a magic link today has no confirmed path to actually receiving it, and nothing in the app would show an error if delivery silently failed — `/signin/sent` (`app/signin/sent/page.tsx`) renders "Check your email" unconditionally once a sign-in attempt passes the allowlist check, regardless of what Resend's API actually did with that specific recipient.

**No Decision Log entry exists yet for "switch to a verified Resend domain"** — this PRD is the first artifact naming the decision at all. Per [[JerkAI - Definition of Ready & Done]]'s "Authoring vs. deciding" section (`DL-2026-07-26-a`), that is fine: deciding is Albert's, and commissioning this PRD directly is the decision to proceed. Logging it with an id is a mechanical follow-up once this ships, not a precondition for drafting or building. The specific sub-decisions this PRD does have to make on Albert's behalf — the exact local-parts, and whether both files ship in one slice or two — are filed as Open Questions with defaults in §8, not silently assumed.

What this slice is NOT: no change to `ALLOWLISTED_EMAILS`, `lib/auth-callbacks.ts`, or sign-in eligibility; no "Connect Whoop" / "Connect Withings" onboarding UI or any other change to what a newly-signed-in user sees (explicitly out of scope, per instruction — that is the separate, still-unauthored "Dashboard Degraded State" PRD, `DL-2026-08-07-a4`); no new environment variable, config table, or admin surface for the sender address; no schema change, no migration; no change to `SYNC_ALERT_EMAIL_TO` or to which single address receives sync alerts; no automated CI test of real Resend delivery (Resend's actual mail delivery to a real inbox cannot run inside CI without a live secret and a live external mailbox — this stays a manual, human-performed check, the same shape [[JerkAI - Build PRD - Extend Sign-In Allowlist]]'s NFR-66 already established for a different live-configuration claim).

## 2. Problem statement

Two files send outbound email from `onboarding@resend.dev`, Resend's shared sandbox domain, which Resend restricts to delivering only to the Resend account's own verified address. Until this session, `ALLOWLISTED_EMAILS` held exactly one address — Albert's own, which is also (per both files' code comments) the Resend account's own address — so every email the app could ever send was already going to the one recipient the sandbox domain would actually deliver to, and the restriction was invisible. `ALLOWLISTED_EMAILS` now holds a second, real address. That second address's owner can request a magic link (the allowlist check passes, `/signin/sent` renders), but nothing in the code path confirms Resend actually delivered the message to them, and the sandbox-domain restriction means it likely did not.

## 3. Objective

Every email this app sends is sent from a Resend-verified `jerkai.app` address. Success = a real, non-account-owner `ALLOWLISTED_EMAILS` recipient requests a magic link and receives it in their own inbox — checked directly, not inferred from a 200 response from Resend's API.

## 4. Functional Requirements — user-centered acceptance criteria

Written as testable Given/When/Then. "The user" here is whichever address holds an allowlisted magic-link request or receives a sync alert — this slice has no signed-in-session-scoped behavior. ### 4.1 Sender address (code-level, falsifiable without a live Resend call)

* **AC-ES1 (bare case)** — Given `sendSyncFailureAlert` sends a sync-failure alert (its one call shape — a subject and a body, no branching on recipient), When it POSTs to `https://api.resend.com/emails`, Then the request body's `from` field carries the new verified-domain address (§8 OQ-1's default: `"JerkAI Sync <sync@jerkai.app>"`) and never `onboarding@resend.dev`.
* **AC-ES2** — Given `auth.ts`'s own source text, When it is inspected for the Resend provider's `from` field literal, Then it equals the new verified-domain address (§8 OQ-1's default: `"JerkAI <noreply@jerkai.app>"`) and never contains `resend.dev` — falsifiable without instantiating NextAuth, the Neon adapter, or any live database connection, since `auth.ts` carries no test file today for exactly that reason (§1).

### 4.2 Live delivery to a real, non-owner recipient (the actual point of this slice)

* **AC-ES3** — Given the `jerkai.app` domain is verified in Resend (NFR-118) and both call sites carry the new sender address (AC-ES1, AC-ES2), When a magic-link sign-in is requested for an `ALLOWLISTED_EMAILS` address that is **not** the Resend account's own verified address — the exact second-recipient scenario this slice exists to fix — Then the email is confirmed present in that address's actual inbox, checked by opening it directly. A 200 (or `{status:0}`-shaped "accepted") response from Resend's own API is not sufficient evidence on its own — Resend can accept a send request for a sandbox-domain sender that it will never actually deliver, which is the exact "check that cannot discriminate the failure from a benign cause" shape [[JerkAI - Build Failure Ledger]] FM-03 already names.
* **AC-ES4** — Given the same post-switch state, When the Resend account's own address (the one recipient that already worked under the sandbox domain) requests a magic link, Then delivery still succeeds — no regression to the one path that was never actually broken.

### 4.3 Regression — sign-in eligibility and alert delivery are unchanged

* **AC-ES5** — Given `lib/auth-callbacks.ts#signIn`'s allowlist check, When this slice ships, Then its behavior (which addresses may request a magic link at all) is unchanged by construction — this slice touches no file `lib/auth-callbacks.ts` or its test imports, and the existing `lib/auth-callbacks.test.ts` suite passes unmodified.
