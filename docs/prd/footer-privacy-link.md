## 0. Scope & Sequencing Note (read first)

`app/layout.tsx` (read directly, 2026-08-19, full 33 lines) is the app's one root layout: `<html>` → `<body className="min-h-full flex flex-col">{children}</body>`, with only font-variable and `metadata` setup — no header, no footer, nothing besides `{children}`. Every page (`/`, `/weekly`, `/daily`, `/log-meal`, `/settings/targets`, `/status`, `/signin`, `/signin/sent`, `/privacy`, and every `/demo/*` route) renders through this one layout; `NavHeader` is rendered per-page today (each page imports and calls it itself), but there is no equivalent shared footer anywhere — confirmed via a repo-wide search for "footer," 2026-08-19: zero matches in `app/`. Albert wants a footer with a link to the existing `/privacy` page (`app/privacy/page.tsx`, already shipped, deliberately public and excluded from the session gate per its own source comment — "WHOOP's Developer Platform requires a privacy policy link, and its OAuth consent flow shows this page to the user before they ever sign in").

**Decision — the footer lives in the root layout (`app/layout.tsx`), not per-page like `NavHeader` (decision, not yet logged — flag for `decision-log` once Albert confirms).** Considered: (A) one footer in `app/layout.tsx`, rendered for every route with zero duplication; (B) a shared footer component, imported and called by each page individually, the same way `NavHeader` is used today. Rejected B: `NavHeader` is per-page because its `active`/`variant` props vary by page (which resolution is active, live vs. demo) — the footer this slice adds has no such per-page variation (a static link to a static page), so replicating `NavHeader`'s per-page-import pattern would mean touching every page file for no behavioral benefit, and — per this codebase's own recurring theme (`docs/codebase.md` §6's "single source of truth" traps) — every future new route added under (B) would need someone to remember to add the footer import, exactly the kind of silent-omission risk the companion "Nav Header Cleanup & Status Page Chrome" PRD is fixing for `/status`'s header right now. (A) also means `/signin` and every `/demo/*` route — none of which call `NavHeader` today — get the footer automatically, which is the more complete outcome and requires no extra decision about which unauthenticated routes should or shouldn't have it. Build A.

**Decision — the footer's only content this slice adds is the privacy link, nothing else (decision, not yet logged).** Considered: (A) exactly one link, "Privacy Policy" → `/privacy`; (B) a fuller footer (copyright line, build/version info, additional links). Albert's request was specifically "a link to the privacy policy in the page footer" — nothing else was asked for, and inventing additional footer content is scope this slice doesn't need to carry. Build A; file (B)'s ideas as an open, unscoped fast-follow rather than guessing what Albert would want in it.

What this slice is NOT: not a redesign or content change to `app/privacy/page.tsx` itself (that page's existing `tests/unit/privacy-page.test.ts` assertions — data sources named, no-sale commitment, contact email — must still pass unmodified); not a per-page or per-variant (live vs. demo) footer; not a footer with any content beyond the one privacy link; not a change to `NavHeader` or to any page's header.

## 2. Problem statement

`app/layout.tsx` renders no footer, and no other file in the app renders a shared one — there is currently no page-chrome element, anywhere in the app, that links to `/privacy` except a direct URL visit or Whoop's own external OAuth consent screen. A signed-in user browsing the app has no in-app way to reach the privacy policy.

## 3. Objective

Every page in the app renders a footer containing a link to `/privacy`, added once at the root layout so no page needs its own copy. Success = a single testable condition: rendering any page through the app's root layout produces markup containing a link whose accessible text is "Privacy Policy" and whose `href` is exactly `/privacy`.

## 4. Functional Requirements — user-centered acceptance criteria

"The user" = any visitor — Albert (signed in), or an unauthenticated visitor on `/signin` or the public `/demo/*` surface, since the footer's presence does not depend on auth state (§0's decision). New id prefix **AC-FT**, numbered from 1 — a new two-letter prefix avoiding collision with the existing jerkai series (`AB`, `AU`, `D`, `M`, `MU`, `N`, `PD`, `PUE`, `ST`, `W`, `WT` — live-verified via `tests/` and `lib/` grep 2026-08-25; plus `AC-PM` (Preview Migration Gap Fix), which never appears in a tests/lib grep since all four of its ACs are ops/manual checks — verified instead against `docs/codebase.md` §7's `AC-` id table; `CV`/`DM`/`MF`/`QT` are jerkai-mcp-only and excluded).

### 4.1 Footer presence and content

* AC-FT1 (bare case) — Given any page rendered through the app's root layout (e.g. `/weekly`, the default landing route — no session, no data, and no specific route required for this property to hold), When the page renders, Then a footer is present containing a link whose accessible text is "Privacy Policy" and whose `href` is exactly `/privacy`.
* AC-FT2 — Given the user is on an unauthenticated route (`/signin`) or a public demo route (`/demo/weekly`, `/demo/daily`, `/demo/about`), When those pages render, Then the same footer with the same privacy link is present — footer presence and content do not vary by auth state or by `NavHeader`'s `variant` prop, since the footer is rendered by the root layout, not by any page or `NavHeader` itself.

### 4.2 No regression to the privacy page or existing pages

* AC-FT3 (regression) — Given the user clicks the footer's "Privacy Policy" link, When navigation completes, Then the browser is at `/privacy`, rendering `app/privacy/page.tsx`'s existing, unmodified content — `tests/unit/privacy-page.test.ts`'s existing three assertions (data sources, no-sale commitment, contact email) pass unmodified, confirming this slice made no edit to that page.
* AC-FT4 (regression) — Given any existing page's own content (everything rendered above the new footer), When this slice ships, Then that content is unchanged — the only diff any existing page's own rendering should show is the new trailing footer element added by the shared layout, not a change inside the page itself.
