## 0. Scope & Sequencing Note (read first)

**This is exactly the gap "Withings Smart-Scale Integration" (PRD 1) named and deferred.** Confirmed this session, both in the vault (PRD 1's own DoD: *"makes `weight`/`bodyFatPct`/`leanBodyMass` resolve their active source per user dynamically (today `DASHBOARD_METRICS` hardcodes `source: "fitdays"`)... fixes the dashboard's currently-inconsistent/missing source tags"*) and directly against the shipped repo: `lib/dashboard/types.ts:14,18-19` still reads `bodyFatPct: { source: "fitdays", ... }`, `weight: { source: "fitdays", ... }`, `leanBodyMass: { source: "fitdays", ... }` — byte-unchanged by PRD 1, exactly as that PRD's own §7 required (`"Do not touch lib/dashboard/types.ts..."`). Meanwhile `biometric_readings` now genuinely holds `source = 'withings'` rows (PRD 1 shipped `migrations/1787782286885_create-withings-tokens.js` and `migrations/1787782287321_widen-source-check-withings.js`), so a Withings-only user's weight/body-fat/lean-mass data exists in the database but is invisible on their own dashboard today — `lib/dashboard/data.ts:40-41`'s query only ever asks for `(source, metric) = ('fitdays', ...)` for these three keys.

**Decision — scale-source resolution is computed once per user, shared uniformly across all three scale metrics, via a small query run before the existing dashboard query — not blended inside the existing CTE.** The existing CTE (`lib/dashboard/data.ts:50-66`) computes the trailing-window axis end date as `max(reading_date)` over its own unfiltered row set (`lib/dashboard/data.ts:59-64`) — this is exactly the mechanism the Multi-User Data Model Retrofit's `NFR-68` already had to protect from cross-*user* contamination (a CTE reading unfiltered rows lets another user's newer reading shift this user's axis). Widening the CTE's `(source, metric)` filter to accept *either* `fitdays` or `withings` for these three keys would reopen the identical landmine one level down — cross-*source*-within-one-user contamination — because a stale or leftover row in the non-active source (e.g. test data, or a user who switched scales) could still leak into the axis computation and the series even after "resolution." Resolving the source **first**, in an isolated query, and then building the same single-concrete-`(source, metric)`-pair-per-key parameter list the existing CTE already expects (`lib/dashboard/data.ts:40-41`) closes this by construction: the main query never sees the non-resolved source's rows at all, for these three keys, exactly as it never sees another user's rows today.

**Decision — resolution picks the source with the most recent `reading_date` across `weight`/`body_fat_pct`/`lean_body_mass` combined (not per-metric); ties break toward `'fitdays'`.** A per-metric resolution (e.g. weight resolves to Withings while body fat % resolves to Fitdays for the same user) would contradict the product decision this slice implements — DL-2026-08-26-a2: *"Each user runs exactly one active scale source at a time... tagged with whichever source that user is actually on."* One shared resolved value, applied to all three keys, makes that split state structurally impossible rather than merely untested. The tie-break exists only for the genuine edge case of simultaneous data in both sources (e.g. a migration day, or leftover test rows) — `fitdays` wins as the deterministic default because every existing user is Fitdays-only today, so this never changes current behavior for anyone who hasn't connected Withings.

**Decision — `DASHBOARD_METRICS`' three scale-metric entries gain a `sources: readonly ["fitdays", "withings"]` field in place of `source: "fitdays"`; every other entry (`dayStrain`, `recoveryScore`, `hrv`, `rhr`, `sleepDuration`) is byte-unchanged.** Confirmed this session: `lib/dashboard/strain.ts:12`'s `DAY_STRAIN_METRIC = { source: "whoop", metric: "day_strain" } as const` and the four Whoop-only entries in `lib/dashboard/types.ts:20-24` have exactly one candidate source each and no resolution ambiguity to solve — widening their shape too would be an unbudgeted, unnecessary touch to already-correct code. This makes `DASHBOARD_METRICS` a genuine union shape (`{source, metric} | {sources, metric}`) that `lib/dashboard/data.ts:40-41`'s parameter-building code must discriminate on — named here as a landmine, not prescribed as a diff (Hard Rule 6): the two entry shapes must not be treated identically by whatever code builds the final `(source, metric)` pair list the CTE consumes.

**Decision — `DashboardData` (`lib/dashboard/types.ts:29-37`) gains exactly one new field, `resolvedScaleSource: "fitdays" | "withings" | null`** — not a per-metric map. This mirrors the "resolved once, applied uniformly" decision above at the type level: there is structurally one answer to "which scale is this user on," never three independent answers that could disagree. `null` means the user has zero rows in either candidate source for these three metrics (never connected any scale) — the same state a disconnected Fitdays-only user is in today, which currently renders `bodyFat` with no tag at all; this slice preserves that exact no-tag behavior for `null`, rather than inventing new placeholder copy (that's "Dashboard Degraded State"'s job, not this slice's — see "What this slice is NOT," above).

**Decision — tag text follows existing, live conventions, not a newly invented format.** Confirmed this session against every current strip tag in `app/ui/dashboard.tsx` (§1, table below): three distinct formats already coexist — a bare source name with no role prefix (`weight`: `"Fitdays"`), a role-prefixed source (`leanMass`: `"Guardrail · Fitdays"`; `recovery`: `"Guardrail · Whoop"`), and an all-caps role-only-with-source label on the one hardcoded strip (`CalorieBarStrip`: `"DRIVER · MANUAL"`, not user-source-driven and untouched by this slice). This slice's new/fixed tags follow the two live source-driven patterns exactly, matching each metric's role as `docs/context.md`'s driver tree already assigns it (confirmed this session): `weight` is `tracked` (no role prefix, matching its own existing `"Fitdays"` convention exactly — so its dynamic tag is `"Fitdays"` or `"Withings"`); `bodyFatPct` has no assigned role in `docs/context.md`'s four-role vocabulary (it's the north-star metric, not a driver/guardrail/tracked leaf) and had no tag at all before this slice — this slice gives it the same bare-source-name treatment as its closest structural sibling, `weight` (`"Fitdays"` / `"Withings"`, no prefix); `leanBodyMass` is `guardrail` (`"Guardrail · Fitdays"` / `"Guardrail · Withings"`, matching its own existing convention with the source swapped in); `hrv`/`rhr` are `guardrail` (`"Guardrail · Whoop"`, byte-identical to `recovery`'s own existing tag — Whoop is these three strips' only source, so this is a static fix, not a resolution); `sleepDuration` is `tracked` (`"Whoop"`, no prefix, matching `weight`'s own bare-name-for-`tracked` convention). None of this is invented — every piece is derived from an existing, live tag string or an existing, live role assignment, cited above.

**Decision — no new unit-conversion code is written.** `lib/dashboard/units.ts:12-14`'s `toPounds` already converts `unit === "kg"` at render time (confirmed unchanged this session, byte-identical to what PRD 1's own §0 described) — a Withings-resolved user's weight/lean-mass rows, stored in kg (PRD 1's `lib/withings-map.ts`), pass through this existing mechanism with zero new code. This slice does not modify `lib/dashboard/units.ts`.

**Decision — `docs/context.md` and `docs/codebase.md` are corrected in this slice's own PR, not merely flagged as owed a second time.** `docs/context.md`'s driver-tree currently states "Weight — *tracked* — from Fitdays via Apple Health" and "Lean body mass — *guardrail* — from Fitdays via Apple Health" (confirmed this session, unchanged since before PRD 1) — this slice is what makes both sentences false for any Withings-connected user, since it's the first slice where a user's dashboard can actually show Withings-sourced weight/lean-mass. ## 2. Problem statement

`biometric_readings` now genuinely holds `source = 'withings'` rows for `weight`/`body_fat_pct`/`lean_body_mass` (shipped by PRD 1), but the dashboard's `DASHBOARD_METRICS` still hardcodes `source: "fitdays"` for all three — so a Withings-only user's own scale data exists in the database and is entirely invisible on their own dashboard. Separately, four of the dashboard's nine strips (Body Fat, HRV, RHR, Sleep duration) render no source tag at all, inconsistent with their five sibling strips.

## 3. Objective

A user's `weight`, `bodyFatPct`, and `leanBodyMass` strips automatically show whichever smart-scale source (Fitdays or Withings) that user actually has data in, tagged accordingly, resolved once and applied consistently across all three — never a mix. Every one of the dashboard's nine strips carries a tag. Success = a Withings-only user's weight/body-fat/lean-mass strips render their real data with a `"Withings"`/`"Withings"`/`"Guardrail · Withings"` tag respectively, a Fitdays-only user sees byte-identical behavior to today, and HRV/RHR/Sleep duration each carry a tag matching their existing sibling strips' conventions.

## 4. Functional Requirements — user-centered acceptance criteria

### 4.1 Per-user scale-source resolution (weight, body fat %, lean body mass)

* **AC-DR1 (bare case)** — Given a signed-in user with zero rows in either `'fitdays'` or `'withings'` for `weight`/`body_fat_pct`/`lean_body_mass`, When the dashboard loads, Then `resolvedScaleSource` is `null`, all three series render their existing empty-state behavior (empty/gap series, `"no data"`/`"no readings"` readouts), and none of the three strips renders a tag — byte-identical to today's disconnected-user behavior.
* **AC-DR2** — Given a user whose only rows for these three metrics are `source = 'fitdays'`, When the dashboard loads, Then `resolvedScaleSource` is `"fitdays"`, all three series render exactly the rows they render today, and the Weight/Body fat/Lean body mass tags read `"Fitdays"`/`"Fitdays"`/`"Guardrail · Fitdays"` — no behavior change for any existing Fitdays-only user.
* **AC-DR3** — Given a user whose only rows for these three metrics are `source = 'withings'`, When the dashboard loads, Then `resolvedScaleSource` is `"withings"`, all three series render that user's Withings-sourced rows, and the same three tags read `"Withings"`/`"Withings"`/`"Guardrail · Withings"`.
* **AC-DR4 (single resolution, never split)** — Given a user with rows in only one of the two candidate sources, Then Weight, Body fat %, and Lean body mass all resolve to that same source in the test's fetched `DashboardData` — one `resolvedScaleSource` value backs all three series (the structural guarantee that no other code path can exist is `DashboardData` carrying exactly one `resolvedScaleSource` field, per NFR-110, not something this single integration test observes directly).
* **AC-DR5 (both-sources tie-break)** — Given a user who has rows in **both** `'fitdays'` and `'withings'` for these three metrics (e.g. leftover data from switching scales), When the dashboard loads, Then exactly one source is selected for all three metrics — the source whose most recent `reading_date`, across all three metrics combined, is newest; when both sources' most recent rows share the identical latest `reading_date`, `'fitdays'` wins. The non-selected source's rows are excluded entirely from the series for these three metrics — never blended into one line.
* **AC-DR6 (axis protection)** — Given a user's non-resolved candidate source has a `reading_date` for one of these three metrics that is newer than any row the resolved source has, When the dashboard's trailing-window axis end date is computed, Then that newer, non-resolved-source reading never shifts the axis — mirrors this app's existing cross-user axis protection (`NFR-68`), extended here to cross-source-within-one-user.

### 4.2 Fixing untagged single-source strips

* **AC-DR7** — Given the HRV and RHR strips (inside the collapsible "Whoop detail" section), When the dashboard renders, Then both carry `tag="Guardrail · Whoop"`, byte-identical to the Recovery Score strip's existing tag.
* **AC-DR8** — Given the Sleep duration strip (inside the same section), When the dashboard renders, Then it carries `tag="Whoop"`, matching the Weight strip's existing bare-source-name convention for a `tracked`-role metric.

### 4.3 Regression scope

* **AC-DR9 (regression scope)** — Given Day Strain, Recovery Score, the Calories strip, and the `/demo/daily` route's (the only demo route rendering per-metric tags — `/demo/weekly` renders through `WeeklyLedger`, which carries no tag rendering at all) Weight/Body fat/Lean body mass tags, Then their existing tags (`"Driver · Whoop"`, `"Guardrail · Whoop"`, `"DRIVER · MANUAL"`, and the demo's static `"Fitdays"`/`"Guardrail · Fitdays"`) and all other rendering are byte-unchanged by this slice — `DEMO_DASHBOARD_DATA.resolvedScaleSource` is set to `"fitdays"`.
