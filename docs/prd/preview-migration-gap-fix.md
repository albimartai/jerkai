## 2. Problem statement

Already diagnosed in [[JerkAI - Build Failure Ledger]] FM-21 — restated here, not re-investigated. The Whoop Multi-Tenancy migration (`migrations/1787083550593_whoop-multi-tenancy.js`, PR #27) added `sync_runs.user_id` and shipped cleanly to production on 2026-08-19 (`migrate-production` succeeded on the merge commit). `/status` had no nav link pointing at it until Nav Header Cleanup & Status Page Chrome (PR #28, squash-merged 2026-08-21 as `f4d2713`) gave the header a "Status" link for the first time in that slice's own history. `app/status/page.tsx`'s `sync_runs` query — untouched by PR #28's diff — has required `user_id` since PR #27 shipped; nobody had clicked into `/status` on a Preview deployment in the weeks between, so nobody had exercised that query against `dev`'s still-unmigrated schema. The first click, during PR #28's own manual spot-check, threw `NeonDbError: column "user_id" does not exist` — a defect in the environment, not in either PR's diff (`jerkai-falsify-diff`'s NFR-85 check on PR #28 confirmed the query was unmodified; production's own schema was independently confirmed current for this exact migration via the `migrate-production` job's run log).

Root cause: `ci.yml`'s `test` job creates a brand-new disposable Neon branch per run, always migrated from an empty database, always torn down; its `migrate-production` job only ever targets `PRODUCTION_DATABASE_URL`. Neither job, nor anything else in the repo, ever migrates `dev` — the branch Preview deployments and local dev both read from. Nothing prompted anyone to run a migration against it after PR #27 merged, because nothing in the process ever names `dev` as an environment that needs one.

## 3. Objective

Three things become true. First, `dev`'s schema is current for `sync_runs.user_id` (and stays current going forward through the process fix below), so `/status` — and any other code path depending on this migration — renders correctly on Preview and in local dev, closing the concrete defect. Second, a future JerkAI build session reading this repo's own `docs/definition-of-ready-and-done.md` — not just a Cowork PM session reading the vault — inherits the requirement that any migration-carrying slice must name every persistent environment beyond CI and production and state whether and how each gets migrated, because the repo copy now matches the vault source that already carries that requirement (landed there 2026-08-21, same day as this incident, per FM-10/12/13/14/15/21). Third, that requirement is visible in the one artifact every PR author actually fills out per PR — the PR template — not only in a DoD file a session has to think to open.

## 7. Deploy plan

Two independent actions, do not conflate them, mirroring the Primary User Email Alert Gap Fix PRD's own convention for exactly this reason:

1. **Ops action (not a repo diff).** Re-confirm live, per §0, that Preview's `DATABASE_URL` is in fact `dev` (`npx vercel env ls preview`, or equivalent), then:
   ```
   npm run migrate
   ```
   `package.json`'s `migrate` script already hardcodes `--envPath .env.local` (`"migrate": "node-pg-migrate --envPath .env.local up"`) — **do not append `--envPath .env.local` again on the command line.** Without an explicit `--` separator, `npm run <script> --envPath .env.local` does not forward `--envPath` to the script at all: npm consumes it as its own config flag and forwards only the bare `.env.local` token, which `node-pg-migrate`'s CLI then reads as a target migration name (`options.file`, `bin/node-pg-migrate.js` lines 400–468) — no migration file is named `.env.local`, so `getMigrationsToRun` (`dist/legacy/runner.js`) matches zero migrations and the command exits 0 printing "No migrations to run!" without touching `dev` at all. Verified by direct reproduction against the installed npm and `node-pg-migrate@8.0.4` in this repo. Confirm which connection string `.env.local` currently holds before running — `npm run migrate` applies to whatever `DATABASE_URL` `.env.local` resolves to, which must be `dev`'s (per the live re-confirmation above), not a stale or different value. This is a live write to a shared, persistent database other in-flight work may depend on — an agent prepares the command, a human runs it or gives explicit go-ahead first, the same convention this repo already applies to any live-credential write (production `DATABASE_URL`, Vercel env vars in the Primary User Email Alert Gap Fix PRD). **Do not run this without Albert's go-ahead in the same session.**
2. **Repo docs (this PRD's diff).** `docs/definition-of-ready-and-done.md` re-sync, `docs/codebase.md` refresh, and the `.github/pull_request_template.md` line — normal branch → PR → CI green → merge path. No migration in this diff, so no separate prod-migration step; CI's disposable-branch tier is unaffected (docs-only changes, §0).
